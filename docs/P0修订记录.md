## 1. accumulator / accumulator-full SCC

### 1.1 审核指出的问题

初版把两个 SCC 都笼统写成「循环」，并据此下了「整个戴森球只有 1 个真实生产循环」的结论。这个表述有两个缺陷：**没有区分循环类型**，且**没有绑定口径**。

### 1.2 复核过程与事实

查数据（`dsp-subset.json`）：

| 配方 | 输入 | 输出 | 建筑 | 工时 |
|---|---|---|---|---|
| `accumulator` | 晶硅 ×3 + 铁锭 ×6 + 超磁环 ×1 | 蓄电池 ×1 | 制造台 | 3s |
| `accumulator-full` | 蓄电池 ×1 | **满电池 ×1** | **能源交换站** | 10s |
| `accumulator-discharge` | 满电池 ×1 | **蓄电池 ×1** | **能源交换站** | 10s |

后两条互为逆过程：`in(r1) == out(r2)` 且 `out(r1) == in(r2)`（按 `{item: amount}` 精确相等）。净物料转化恒为零。

在 `stats.py` 里加了 `is_roundtrip()` 判定函数，规则就是上面这条精确相等。首次实现写错过一版（判据写成了「产出物 == 目标物品」），在 `case_g` 输出里表现为「往返配方=None」，被自查发现后修正。

### 1.3 修订后

- **分类**：`{hydrogen, refined-oil}` = 物料生产循环；`{accumulator, accumulator-full}` = 储能充放电往返。
- **纳入决策**：第一版**不纳入**后者。三条理由（写进 §4.5.1）：净物料流为零、不是持续生产环节（唯一非回环用途是建造轨道采集器，一次性消耗）、成本在能量侧不在物料侧。
- **实现方式**：在数据层用 `excludedByDefault` 标记 `accumulator-full` / `accumulator-discharge`，而不是靠隐式规则过滤。这条已进 §13.10 待确认项。
- **口径绑定**：新增 D.1.1 节，给出四组口径的实测对照。

### 1.4 口径敏感性实测（新增证据）

| 口径 | 配方数 | 图规模 | SCC | 物料生产循环 |
|---|---:|---|---:|---|
| R0 全量（含 307 条 `technology`） | 496 | 111 / 1253 | 2 | 1 |
| **R1 剔除 `technology`（主口径）** | **189** | **110 / 444** | **2** | **1** |
| R2 每物品仅保留首选配方 | 173 | 104 / 424 | **0** | **0** |
| R3 剔除 `energy-exchanger` 配方 | 187 | 109 / 442 | 1 | 1 |

**R2 是这次复核最重要的发现**：单主配方口径下循环**完全消失**。这说明「单主配方」不是简化，而是把循环问题从视野里删掉——直接支撑了「多配方能力必须一开始就有」，也解释了 DSP Helper 为什么永远遇不到循环。

### 1.5 修订后措辞

> 在 DSP `0.10.29.21950` 的 FactorioLab 数据集上，剔除 307 条 `technology` 研究配方后，对 189 条生产配方构图，**物料生产循环恰好 1 个**（`{hydrogen, refined-oil}`），另有 **1 个储能充放电往返环**（`{accumulator, accumulator-full}`，不纳入求解器）。超出该数据版本或该过滤口径不作保证。

## 2. LP 松弛变量的目标函数与可执行性

### 2.1 审核指出的问题

初版让所有物品都能被 `s⁺`（外购）和 `s⁻`（放空）自由调节，并用 `(100, 10, 1)` 的加权和做目标函数。两个问题：**游戏里买不到/扔不掉的物品也被允许买/扔**；**权重的数量级没有依据**。

### 2.2 修订内容：策略由数据决定

新增 `case_g`，从数据字段推出两个集合：

| 集合 | 判据 | 规模 |
|---|---|---:|
| 可无限外购 `importable` | 被 `flags=['mining']` 的配方产出 | **18 项** |
| 可焚烧放空 `ventable` | 物品带 `fuel` 字段 | **27 项** |

依据：矿脉/海洋/气态巨星/原油渗井在游戏里可持续采集；只有可燃物能进火力发电站烧掉，不可燃固体只能堵线，游戏没有「删除物品」的原生操作。

`i ∉ importable` 时 `s⁺[i]` 列整列置零；`i ∉ ventable` 时 `s⁻[i]` 整列置零。本模型涉及的三个边界物品：精炼油（不可外购、可烧）、氢气（可外购、可烧）、高能石墨（不可外购、**可烧**）。

### 2.3 修订内容：目标函数改为字典序

初版：`min 100·Σs⁺ + 10·Σs⁻ + 1·Σc·x`。

问题：100/10/1 是人为标定，换个量级就换答案。实测证据（同一模型）：

| 目标函数 | 外购 H2 | 放空合计 | 运行成本 |
|---|---:|---:|---:|
| (100, 10, 1) | 0.000 | 0.833 | 12.333 |
| (1, 1, 1) | 1.250 | 0.000 | 11.500 |
| (1, 100, 1) | 1.250 | 0.000 | 11.500 |
| **字典序 外购→放空→运行** | **0.000** | **0.833** | **12.333** |

**三组权重给出两种不同方案**，而「一次外购抵几次放空」在游戏机制里没有客观答案。

修订后用字典序（preemptive / sequential）：先解①并把最优值锁成等式约束，再解②，最后解③。优先级显式、与量纲无关。实现为 `linalg.lexicographic_min()`。

### 2.4 修订后措辞（§7.2.1）

给出完整的 LP 子模型定义：变量域、约束形式、策略集合、三层目标、以及「不可行时必须指出是哪一行矛盾」的诊断要求。

## 3. SCC 外副产品的边界处理

### 3.1 审核指出的问题

初版把高能石墨的富余简单写成「放空 0.8333/s」，没有说明它**为什么不在 SCC 内**、以及它如何与其他节点的需求合并。

### 3.2 复核结论

`case_g` 用收缩图自动算出边界：

```
分量 {refined-oil, hydrogen}   类型: 物料生产循环
  入边物品（外部供给）: coal, critical-photon, crude-oil
  出边物品（对外供应）: antimatter, deuterium, energetic-graphite, graphene
```

`energetic-graphite` 是**出边物品**：由 `x-ray-cracking` 产出，但消费者（`graphene` / `plastic` / `diamond`）全在环外。

### 3.3 修订后：三种处置方式的对比

| 建模 | plasma | xray | 外购 H2 | 放空 EG | 说明 |
|---|---:|---:|---:|---:|---|
| M1 只解 SCC 内部 | 6.1667 | 5.8333 | 0 | — | 差额 0.8333 **无任何约束记录** |
| M2 EG 进全局平衡 + 允许焚烧 | 6.1667 | 5.8333 | 0 | 0.8333 | 可行 |
| M3 EG 进全局平衡 + 禁止焚烧 | 5.7500 | 5.0000 | 1.2500 | 0 | 可行，改从气态巨星补氢 |

**M1 是隐形废弃物**：数字对得上，但界面上不显示那 0.8333，玩家按它建厂会堆一堆石墨。M2 与 M3 是两条真实可选路线，取舍应呈现给玩家。

### 3.4 修订后：算法层面的处理

§7.2 求解顺序新增两步：
- 步骤 4 `classifySCCs()`：按往返判定剔除状态转换环；
- 步骤 6：求解子图取 **SCC ∪ 入边物品 ∪ 出边物品**，而不是 SCC 本身；
- 步骤 7：出边物品的产出**先冲抵同物品的外部需求，余额才计入 `surplus`**。

## 4. 数据集统计口径

### 4.1 审核指出的问题

附录 A.3 出现两处自相矛盾：
- 物品总数 182，但「产出配方数分布」合计 181；
- 摘要写「多配方物品 18」，而分布里 2+3+4 档合计只有 17。

### 4.2 根因

分布统计的代码只枚举了 `k ∈ {0,1,2,3,4}`：

```python
{ k: sum(1 for i in ds.items if len(ds.recipes_for(i)) == k) for k in (0,1,2,3,4) }
```

**漏掉了产出配方数 ≥ 5 的物品。** 实测有 1 个物品落在这一档：**氢气，8 条产出配方**（`plasma-refining` / `x-ray-cracking` / `graphene-advanced` / `mass-energy-storage` / `gas-giant` / `gas-giant-hydrogen` / `ice-giant` / `ice-giant-hydrogen`）。

所以：182 = 16+148+13+3+1+**1(8条档)**；18 = 13+3+1+**1**。**摘要的 18 是对的，分布的 181 是错的。**

### 4.3 修订做法

不是改数字，而是**换机制**：
- 新增 `stats.py` 作为唯一口径来源，报告中的数字全部由它生成；
- 用 `Counter` 直接统计，不做桶上限假设；
- 加断言 `Σ分布 == 物品数`，不成立直接抛异常；
- 输出三态：人类可读（默认）、口径对照（`--regimes`）、机器可读（`--json`）。

### 4.4 修订后数字

```
物品 182 · 配方 189 · 建筑 53 · 增产剂 6

产出配方数分布
    0 条 : 16      4 条 :  1
    1 条 : 148     8 条 :  1   ← v1 遗漏的桶（hydrogen）
    2 条 : 13      -----------
    3 条 :  3      合计  182

多配方物品（≥2 条）: 18
```

并在附录 A.3 中补充了完整口径表（配方/物品/建筑/图四个维度的过滤规则）。

## 5. 自研 LP 求解器的论证

### 5.1 审核指出的问题

初版把「自研单纯形」直接写进技术选型表，理由是「Python 原型跑通，225 行，通过 4 组标准测试」。这是不充分的：**Python 原型通过不代表 TypeScript 正式实现已经验证**。

### 5.2 新增：与 GLPK 的对照验证

**对照求解器**：GLPK 5.0，从 `ftp.gnu.org` 下载源码、本机 `configure && make && make install` 编译到 `/tmp/glpk`。选它是因为 FactorioLab 的生产求解器就是 GLPK 的 WASM 移植（`glpk-ts`）——与 GLPK 一致，等价于与参考项目的求解内核一致。

**方法**：两侧从同一个 `LPProblem` 数据结构出发，一侧调 `linalg.simplex_min`，一侧写成 CPLEX LP 格式喂 `glpsol`。另做**独立可行性校验**（把解代回原模型，不依赖任何求解器）。

**8 个模型，六类场景**：

| 场景 | 自实现 | GLPK | 判定 |
|---|---|---|---|
| F1 可行·唯一最优 | optimal / −12.000000 | optimal / −12.000000 | PASS |
| F2 不可行 | infeasible | infeasible | PASS |
| F3 无界 | unbounded | unbounded | PASS |
| F4 退化（Beale 循环示例） | optimal / −0.050000 | optimal / −0.050000 | PASS |
| F5 多解·无穷多最优 | optimal / 0.000000 | optimal / 0.000000 | PASS |
| F6a DSP·氢气回路 | optimal / 20.666667 | optimal / 20.666670 | PASS |
| F6b DSP·多配方择优 | optimal / 3.000000 | optimal / 3.000000 | PASS |
| F6c DSP·无松弛不可行 | infeasible | infeasible | PASS |

### 5.3 对照中发现的一个真实坑

首轮 F3 两侧不一致：自实现 `unbounded`，GLPK `UNDEFINED`。

排查：**GLPK 的预解器在判定无界时返回 `UNDEFINED`**，与「不可行」共用状态码。加 `--nopresol` 后 stdout 输出 `LP HAS UNBOUNDED PRIMAL SOLUTION`，状态正确。

这条已写入实现约束：选 GLPK 系方案必须关预解或读日志消歧，否则「无界」会被误判成「不可行」。

### 5.4 选型降级

| 项 | v1 | v2 |
|---|---|---|
| 选型状态 | **自研单纯形**（已锁定） | **待定**（候选方案） |
| 依据 | Python 原型通过 4 组测试 | Python 原型 + GLPK 8 模型对齐 |
| 接口 | 无 | `LpBackend { solve(problem) → result }` |
| 备选 | 未考虑 | `javascript-lp-solver` / `glpk-wasm` |
| 锁定条件 | — | TS 版实现完成 + 同一套 8 模型回归通过 |

### 5.5 明确标注为「仍未验证」的部分

1. **TypeScript 正式实现尚未编写**，位宽、除法精度、数组越界、大模型性能均未覆盖；
2. **规模边界未测**：本案例最大 3 约束 × 9 变量，真实规划可能上百变量；
3. **未编译为 WASM 交付形态**，包体积与启动开销未知。

## 7. 未被推翻的结论（明确保留）

以下结论在本轮修订中**未改动**，仍按原报告执行：

1. 三层计算架构（递归 / 矩阵 / 优化）与模块划分。
2. 技术栈：React 19 + TS + Vite + `@xyflow/react` 12 + Zustand + ELK.js + IndexedDB + Web Worker + Vitest。
3. 画布坐标不参与计算、节点移动不触发重算、求解结果永不落盘。
4. 节点 `data` 只存引用（`recipeId`），端口在渲染层派生。
5. 连线必须做三阶段校验（结构 / 物品类型 / 语义），拒绝落边而非标记。
6. 取整不向下游传播（案例 A 的 3.2 倍误差实证仍在）。
7. 矿石由 `mining` 配方建模，需显式截断层。
8. 多配方择优必须在一版就有（案例 B 的 52 台 vs 5 台实证仍在）。
9. 图必须能表达共享中间产物（案例 C 的 10 个冗余节点实证仍在）。
10. 许可证结论：Graph-Calc / DSP Helper 零 LICENSE 只能作设计研究；0fuz 的 MIT 以仓内 LICENSE 为准；dsp-calct 是 fork 需追溯上游；图标与中文名不在 MIT 范围内。

## 10. 一句话总结

本轮的实质变化不是「改了几个数字」，而是三件事：

1. **给结论加上了适用条件**——「唯一循环」现在带数据版本、过滤口径与循环类型三重限定。

### 12.2 问题二：LP 迭代上限

**修改前**（`lib/linalg.py`）

```python
# 第一阶段
if st != "optimal":
    return {"status": "unbounded" if st == "unbounded" else "infeasible", ...}
# 第二阶段
if st == "unbounded":
    return {...}
# 之后无条件
return {"status": "optimal", "x": x, "z": z, "iters": iters}
```

**复现**（`min x, s.t. x+y=1`，真最优 0）

| 预算 | 修改前 | 修改后 |
|---|---|---|
| 1 | `infeasible` | `maxiter`（phase=2，无解返回） |
| 2 | `optimal z=1` | `optimal z=0` |
| 5000 | `optimal z=0` | `optimal z=0` |

**修改后**

1. 新增第四态 `"maxiter"`，与 `optimal / infeasible / unbounded` 并列，`x`、`z` 恒为 `None`；
   附带 `phase`（1/2）与 `reason`。
2. 两阶段任一命中都原样传出，不再被 `else` 分支吞掉。
3. **预算改为按枢轴次数计**。旧实现把「最后一次进入循环、发现已最优、返回」也算一次迭代，
   导致 `max_iter=2` 明明够用却被判超限。这是第二个 bug，审核未提及但修第一处时暴露出来。
4. `lpio.solve_self(max_iter=…)` 透传该参数，`lexicographic_min` 也原样传播。
5. 案例 F 的判定改成不变量而非固定期望：
   **对任意预算，要么 `maxiter`，要么 `optimal` 且值确实最优**，扫描预算 1..6。

**附带修正**：`lpio._STATUS_MAP["UNDEFINED"]` 从 `infeasible` 改为 `unknown` —— 把 GLPK 的「未定」默认当成
「不可行」，与本次修的是同一类错误。

### 12.3 问题三：燃料与放空策略

**修改前**

```python
ventable = { i | item[i].fuel ≠ null }      # 27 项，一律可烧
```

**事实核对**（`vendor/dsp-data.json`，审核数字全部确认）

| `fuel.types` | 数量 | 设施（`machine.fuel_types`） |
|---|---:|---|
| `chemical` | **21** | `thermal-power-plant` |
| `nuclear` | 1 | `mini-fusion-power-plant` |
| `antimatter` | 2 | `artificial-star` |
| `lens` | 2 | 不是燃料 —— 是 `ray-receiver-pro.consumption` 的消耗品 |
| `accumulator` | 1 | `energy-exchanger` 的放电配方 |

> 审核说「现有 27 项中只有 21 项是 chemical，另外包含满蓄电池、透镜、核燃料和反物质燃料等」——
> 逐项核对后完全成立：1 + 1 + 2 + 2 + 21 = 27。

**根因之一**：`extract_subset.py` 在抽取子集时把 `machine.fuelTypes` 与 `machine.consumption`
两个字段**裁掉了**。没有这两个字段，实现里根本无法判断「这台建筑接受哪种燃料」，
于是只能用 `fuel != null` 这种粗判据。
**修法**：抽取器保留这两个字段（不改数值，只保留原有信息），重新生成子集。

**修改后**

1. 新增 `lib/policy.py`：`build_policy()` 从数据推导三类处置路径
   （`burn` / `consume` / `transform`），并给出 `importable`（有 mining 来源）与 `burn_by_type`。
2. `can_burn_chemical(item)` 成为「能否进火电站」的唯一判据，被案例 G/H 的 LP 使用。
3. 案例 G 重写：打印建筑接受类型、逐项处置路径、覆盖性检查、焚烧开关对照。
4. 报告 §4.8.1 表格、摘要第 10 条、P1 数据模型（`ventRoute` 字段）同步修正。

**精炼油 / 氢气 / 高能石墨的结果复核后保留**：三者都是 chemical，进火电站合法，
案例 G/H 的 0.8333/s 放空结论不变。

### 12.4 问题四：无 GLPK 时的验证与结论

**修改前**

```python
ok = True
if glpsol:
    ok = ...                        # 只有装 GLPK 时才检查
if feas_self[0] is False:
    ok = False                      # x 为 None 时永不触发
```
以及结论文本里硬编码的 `"与 GLPK 在上述 8 个模型上状态与目标值全部一致"`。

**后果**（审核已模拟）：把求解器改成「全部返回 infeasible」，无 GLPK 环境下 8 项仍全 PASS。

**修改后**

1. 新增 **ORACLE**：每个模型的预期状态 + 预期最优值，**独立于被测求解器**给出，
   推导写在源码注释里（F1/F2/F3/F5/F6b/F6c 手算；F4/F6a 由顶点穷举）。
2. 判定一律对 ORACLE 做，不再以「两边一样」为准 —— 两个实现同时错时，「一致」没有意义。
3. 新增**第二套独立算法** `linalg.enumerate_optimum()`：穷举所有基可行解，
   不做枢轴、不用入门规则，与单纯形算法不同源。8 个模型上两套算法结果完全相同。
4. GLPK 降为**可选的第三重佐证**：未安装时记为 `SKIP`，不计入 PASS。
5. 结论文本由本次执行结果生成：
   `f"自实现与 ORACLE 一致: {n_pass}/{len(detail)} 个模型"`，GLPK 缺失时写「未执行 → SKIP」。

**两种环境的实测**

| 环境 | 案例 F 判定数 | 总体 |
|---|---:|---|
| 有 GLPK | 13（含 F11 第三方对照） | PASS |
| 无 GLPK | 12（F11 → SKIP） | PASS |

无 GLPK 时若把求解器改成全 infeasible，现在会失败 —— 因为 ORACLE 检查不依赖 GLPK。

## 13.1 问题一：负射线证书的数学条件

### 13.1.1 复验给出的反例

```text
min -x
-x = -1
x >= 0
```

唯一可行点 `x=1`，最优值 `-1`，显然有界。v3 的 `has_negative_ray()` 返回 `True`。

### 13.1.2 独立复现（修复前）

```bash
cd docs/p0-evidence
python3 - <<'PY'
import sys; sys.path.insert(0, "lib")
import linalg
print(linalg.has_negative_ray([-1], [[-1]]))      # True  ← 误报
PY
```

原始输出（`outputs/v4_repro/r1_ray_pre_fix.log`）：

```text
=== 反例 1: min -x  s.t.  -x = -1,  x>=0 ===
真实解: x=1, z=-1, 有界
has_negative_ray -> True
simplex         -> optimal z= -1.0 x= [1.0]
glpsol found    -> /tmp/glpk/bin/glpsol
glpk            -> optimal x= [1.0]
```

自实现单纯形与 GLPK 都正确，**只有那个「证书」是错的** —— 这正是「独立基准必须算法不同源」的价值。

### 13.1.3 原因

模型是等式约束 `A·x = b`。可行方向必须满足 `A·d = 0`；
v3 用的是 `A[:,j] <= 0`，等价于允许 `A·d <= 0`，方向会破坏等式。
反例中 `A·e_x = -1 ≠ 0`，沿 `e_x` 走一步就离开可行域。

还有第二层错误：v3 把「存在下降方向」直接当成「问题无界」。**不可行问题也可能有下降方向** ——
`min -x, -x = 1, x >= 0` 的列条件成立，但可行域为空，正确结论是 `infeasible`。

### 13.1.4 修复

`lib/linalg.py`：

| 函数 | 作用 |
|---|---|
| `verify_ray_certificate(c, A, b, x0, d)` | 逐项验证 6 条：`A·x0=b`、`x0>=0`、`A·d=0`、`d>=0`、`d≠0`、`c·d<0`；另用 `t∈{0,1,10,1000}` 采样验证 `x0+t·d` 可行且目标严格下降 |
| `prove_unbounded(c, A, b)` | **先验可行性、再验方向**：第 1 步解 `min 0` 取 x0（infeasible 直接返回）；第 2 步解 `min c·d s.t. A·d=0, Σd=1, d>=0` 构造 d，再交证书复核 |
| `legacy_column_ray_unsound()` | 旧判据（**仅供回归演示会误报**，任何求解路径不得调用） |

F3 的证书现在是显式见证，不是从求解器抄回来的：

```python
RAY_CERTS = {"F3 无界": {"x0": [0, 0], "d": [1, 1]}}
```

逐项输出（`case_f` 日志）：

```text
[ok] A·x0 = b（第 0 行）: 0 vs 0
[ok] x0 >= 0: [0, 0]
[ok] A·d = 0（第 0 行）: 0 vs 0
[ok] d >= 0: [1, 1]
[ok] d != 0: 方向非零
[ok] c·d < 0: c·d = -2
[ok] 沿方向采样：x0+t·d 可行且目标严格下降: t=0: z=0; t=1: z=-2; t=10: z=-20; t=1000: z=-2000
```

### 13.1.5 回归（F12–F15）

| 编号 | 模型 | 期望 | 结果 |
|---|---|---|---|
| F12 | `min -x, -x=-1`（有界反例） | 旧判据 True（误报）、新判定 `bounded`、单纯形 `optimal z=-1` | PASS |
| F13 | F3 的证书 `x0=(0,0), d=(1,1)` | 六条全成立、`c·d=-2` | PASS |
| F14 | `min -x, x-y-z=0`（真无界，射线 `(1,1,0)` 非单位列） | 旧判据 **False（漏报）**、新判定 `unbounded` | PASS |
| F15 | `min -x, -x=1`（方向存在但不可行） | 旧判据 True、新判定 `infeasible`（**不是** unbounded） | PASS |

故障注入 `P0_FAULT=ray_column_only` 可让 F12 失败（exit=1），证明这条断言有效。

## 13.2 问题二：顶点枚举对冗余约束的处理

### 13.2.1 复验给出的反例

```text
min x
x = 1
x = 1
x >= 0
```

正确答案 `x=1, z=1`。v3 的 `enumerate_optimum()` 返回：

```text
status = no_vertices
n_feasible = 0
```

两行一列，`C(1,2)` 不存在 —— 枚举不出基，但枚举不出 ≠ 不可行。

### 13.2.2 独立复现（修复前）

`outputs/v4_repro/r2_enum_pre_fix.log`：

```text
=== 反例 2: min x  s.t.  x=1, x=1, x>=0 ===
真实解: x=1, z=1, 唯一可行极点
enumerate_optimum -> {'status': 'no_vertices', 'z_best': None, 'x_best': None, 'n_feasible': 0}
simplex           -> {'status': 'optimal', 'x': [1.0], 'z': 1.0, ...}

=== 反例 2b: x=1, x=2 (矛盾) ===
enumerate_optimum -> {'status': 'no_vertices', ...}
simplex           -> {'status': 'infeasible', ...}
```

第二个反例更说明问题：结论（不可行）碰巧对，但**理由是错的** ——
它不是因为检出了矛盾，而是因为枚举不出基。同样的 bug 在可行模型上就会直接误判。

### 13.2.3 修复

`lib/linalg.py`：

1. 新增 `_rank_of_rows()` 与 `independent_rows()`：贪心选出线性无关的**原始行索引**与行秩；
2. `enumerate_optimum()` 先对 `[A|b]` 做 RREF，检出 `0 = c (c≠0)` 即判 `infeasible / rref_contradiction`；
3. 按**有效行秩 r**（而不是原始行数 m）选 r 列枚举，用独立行组成的 `A_r, b_r` 求解；
4. 一致但无 BFS 时判 `infeasible / no_bfs` —— 有定理支撑：`{x>=0: Ax=b}` 非空 ⇒ 必存在基可行解；
5. 规模超限返回 `too_large`、空模型/行秩 0 返回 `unsupported`，**两者都不得当作不可行**。

状态语义现在是显式的：

| status | 含义 | 能否作为「不可行」的证据 |
|---|---|---|
| `has_vertices` | 至少一个 BFS，`z_best` 为其中最小目标值 | — |
| `infeasible` + `rref_contradiction` | 增广矩阵矛盾 | **能**（直接证明） |
| `infeasible` + `no_bfs` | 一致但无 BFS | **能**（定理） |
| `too_large` / `unsupported` | 未枚举 / 不支持 | **不能**（结论未知） |

### 13.2.4 回归（F16–F19）

| 编号 | 模型 | 期望 | v3 行为 |
|---|---|---|---|
| F16 | `x=1, x=1` | `has_vertices, z=1, rank=1` | `no_vertices` |
| F17 | `x=1, x=2` | `infeasible / rref_contradiction` | `no_vertices` |
| F18 | `x=1, 2x=2` | `has_vertices, z=1` | `no_vertices` |
| F19 | `max_bases=0` | `too_large`（不给出 z、不判 infeasible） | `too_large` |

F16–F18 全部从 FAIL 转为 PASS；F19 守住「不知道就说不知道」。
故障注入 `P0_FAULT=enumerate_raw_rows` 可让 F16 失败，证明断言有效。

### 13.2.5 八个 LP 模型的验证方法必须逐项说明

v3 的日志写「独立基准 枚举 z=…」，读起来像「8 个模型都由枚举证明」。实际不是。修正后 `case_f` 打印：

```text

  顶点枚举                     5 个: F1, F4, F5, F6a, F6b

  * 注：无界模型**不能**由顶点枚举判定 —— 无界问题同样有可行极点，
    枚举只给出「极点上最小的 z」。F3 的无界性由射线证书证明。
```

`F3` 的枚举结果（2 个可行极点、`z_best=0`）也打印出来，但**明确标注不能作为无界证据**。

## 13.3 问题三：环外副产物回供与全局守恒

### 13.3.1 复验给出的场景

```text
目标: 能量矩阵 2/s + 反物质 1/s

energy-matrix       ×2.0/s : 2 EG + 2 H2 → 1 能量矩阵
mass-energy-storage ×0.5/s : 2 临界光子 → 2 反物质 + 2 H2

氢气：耗 4.0/s，副产 1.0/s ⇒ 净需求 3.0/s
```

### 13.3.2 独立复现（修复前）

`outputs/v4_repro/r3_byproduct_pre_fix.log`：

```text
=== analyze 目标 能量矩阵2/s + 反物质1/s ===
  demand: {'energetic-graphite': 4.0, 'hydrogen': 4.0, 'refined-oil': 0.0}
  trace:
    · energy-matrix 2.0000/s ← energy-matrix ×2.0000
      ⊣ hydrogen +4.0000/s（边界物品，停止展开）
    · antimatter 1.0000/s ← mass-energy-storage ×0.5000
      · critical-photon 1.0000/s ← critical-photon ×0.1667
```

`mass-energy-storage` 被展开了（说明能拿到副产），但产物从未累加 ——
氢气需求停在 4.0，整张图多出 1.0/s 无人认领。

### 13.3.3 原因

`derive_demand()` 只在「遇到边界物品」时累加**输入**需求，从不记录配方的**输出**。
`mass-energy-storage` 的氢气是副产，不在任何人的输入列表里，于是被丢掉。
更麻烦的是 LP 自己的三行（RO / H2 / EG）仍然平衡 —— 因为需求就是按 4.0 建的，
**局部守恒天然自洽，看不出缺口**。

### 13.3.4 修复

`lib/boundary.py`：

| 变更 | 说明 |
|---|---|
| `ExternalRun` 数据类 | 每条环外配方的 `rate` + **全部** `inputs` / `outputs`（不只边界物品） |
| `expand_external()` | 递归展开时按配方聚合速率；分别产出 `gross_in`（边界物品被消耗）、`gross_out`（边界物品被副产）、`target_direct`、`raw` |
| 净需求公式 | `b[i] = gross_in[i] + target_direct[i] − gross_out[i]` |
| `surplus` | `b[i] < 0` 时记录「副产超过消耗」的差额，日志标注「须由环内吸收或放空」，不静默丢弃 |
| `global_balance()` | 环内 LP + 环外展开拼成一张账，逐物品核对残差（Fraction 精确比较） |
| `describe()` | 打印环外每条配方的速率与全部输入输出、边界物品的「消耗 + 目标 − 副产 = 净需求」 |

修复后的同一场景：

```text
环外展开配方（3 条，运行时速率与全部输入输出）:
  energy-matrix            ×  2.0000/s   Energetic Graphite×4.0000, Hydrogen×4.0000  →  Energy Matrix×2.0000
  mass-energy-storage      ×  0.5000/s   Critical Photon×1.0000  →  Antimatter×1.0000, Hydrogen×1.0000
  critical-photon          ×  0.1667/s   —（无物料输入）  →  Critical Photon×1.0000
边界物品净需求（外部消耗 + 目标直接 − 外部副产）:
  Energetic Graphite     4.0000 +   0.0000 −   0.0000 =   4.0000/s
  Hydrogen               4.0000 +   0.0000 −   1.0000 =   3.0000/s
  Refined Oil            0.0000 +   0.0000 −   0.0000 =   0.0000/s
```

### 13.3.5 全局守恒的覆盖范围（必须说清楚）

`global_balance()` 的账目恒等式：

```
产出 = 环内净流量 + 环外副产 + 外购
消耗 = 环外消耗   + 目标需求 + 放空
残差 = 产出 − 消耗         （必须为 0）
```

| 场景 | 覆盖物品 | 覆盖内容 | 结果 |
|---|---:|---|---|
| 卡西米尔 1/s | 13 | 3 个边界行 + 目标 + 环外 10 条配方的全部输入输出 | 残差全 0 |
| 能量矩阵 2/s + 反物质 1/s | 6 | 3 个边界行 + 2 个目标 + 环外 3 条配方 | 残差全 0 |

**不覆盖**（写进日志，不假装闭合）：

- 环内配方的**入边原料** `coal` / `crude-oil`：按「边界外无限供给」处理，不建平衡行；
- 没有任何配方的外部原料（如 `log` / `plant-fuel`）：单列在 `raw_inputs`。

所以准确的表述是「在**该子图 + 其外部展开**范围内闭合」，不是「整张生产图闭合」。

### 13.3.6 回归（H7–H12）

| 编号 | 内容 | 期望 | 结果 |

| H7 | 氢净需求 | 消耗 4 − 副产 1 = **3** | PASS（v3 记 4） |

## 13.8 本轮结束时仍未解决

1. **全局物料账的闭合范围有限**（§13.3.5）。环内入边原料（coal / crude-oil）不建行；
   只验证了 3 个目标场景；未验证「同一物品既外购又副产」的账目行为。
2. **顶点枚举有规模上限**（rank ≤ 5、n ≤ 24、组合数 ≤ 2e5）。超过上限只能返回 `too_large`，
   大规模模型如何获得「算法不同源」的独立基准仍未解决（对偶证书 / 区间算术 / 第二实现，均未评估）。
3. **处置通道只建模 chemical 燃烧**（§13.4 第 3 条）。核燃料棒、反物质燃料棒、透镜消耗、
   满电池↔空电池均未进 LP；状态往返需要成对列，单物品 `s⁻` 会算错账。
4. **边界自动化只在单物料循环上验证**。第二循环、部分外购混合比例、>10 个边界物品未测。
5. **LP 第③层成本口径仍未定**（报告 §13.5）。字典序前两层不受影响。
6. **TS 实现仍未写**，选型保持「待定」；TS 版必须一并通过 F12–F19 才允许替换默认后端。
7. **故障注入覆盖 10 条守卫**，案例 E 的 8 项与统计脚本的多数断言仍未逐一做「改坏能否发现」的验证。

以上 1–3 条是本轮新增的、由修复本身带来的边界；4–7 条是 v3 已有、本轮未改变的缺口。
