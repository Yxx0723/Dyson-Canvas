## 0. 摘要

### 0.1 结论先行

本报告用「源码阅读 + 独立复算」两条独立证据链，验证了原技术方案的可行性，并对其中 **7 处** 给出了修订意见。最重要的 8 条结论如下：

1. **三层计算架构成立，但层的边界要重画。** 递归层负责 DAG；矩阵层只负责 **1 个物料生产循环**（`{hydrogen, refined-oil}`）；LP 层负责 **18 个拥有多配方的物品** 与副产品的处置取舍。不需要通用求解器。

   > **口径声明**：上述「唯一物料生产循环」限定于 **DSP 0.10.29.21950 + FactorioLab 数据集 + 剔除 307 条 `technology` 研究配方后的 189 条生产配方**。换口径结论会变：若每物品只保留首选配方，循环在图上**完全消失**（SCC=0）；若不剔除 `technology`，节点数从 **174** 变为 **481**、边从 444 变为 1253，但循环集合不变。
（v3 修正：v2 报告的 110/111 是**节点统计错误**，构图时只为输入物品建键，漏掉了纯输出物品；边数不受影响。）完整对照见 §4.5.1 与 `outputs/dataset-stats-regimes.log`。

2. **图中有两个强连通分量，但只有一个是「生产循环」。** `{hydrogen, refined-oil}` 是物料转化；`{accumulator, accumulator-full}` 是**储能充放电往返**——`accumulator-full` 配方（1 蓄电池 → 1 满电池，能源交换站）与 `accumulator-discharge` 配方（1 满电池 → 1 蓄电池）互为逆过程，净物料变化为零。第一版求解器**不纳入**后者，理由见 §4.5.1。

3. **高斯消元不足以表达真实需求，必须用线性规划。** 0fuz/dsp-calc 强制系统为方阵（`n === m`，不方阵直接报错）。真实场景里「外购」与「放空」是必需的松弛变量。

> **v3 限定**：v2 此处写「加入后问题才总是可行」，这是**无条件的错误陈述**。
> 正确表述是：在「每个平衡行都允许外购或放空」这一**演示假设**下问题才可行；
> 一旦按游戏机制收紧（例如硫酸既买不到也烧不掉），问题仍可能不可行 —— 案例 F 的 F6c 就是这种情形。
> 可行性来自「松弛列被允许」，不来自「松弛变量」这个概念本身。

4. **「设备数量向上取整」不能作为默认行为，更不能向下游传播。** 三份参考实现三种口径。案例 A 实测：层层取整把 3.5 台熔炉放大成 **10.5 台**，原料从 2/s 放大到 6.33/s（3.2 倍）。必须作为显式策略，且默认关闭传播。

5. **矿石不是「无配方物品」。** FactorioLab 把矿脉建模为 `flags=['mining']` 且输入为空的配方（`iron-vein` 等 22 条）。若不加区分地递归，每种矿都会变成一台采矿机，「需要多少矿石」这个玩家最关心的数字就消失了。必须提供显式截断层。

6. **画布的图模型必须是「引用」，不是「拷贝」。** Graph-Calc 把配方端口反范式化写进 `node.data`，因此不得不写一个 257 行的 `propagateProjectDataToNodes()` 在每次定义变更时全量重算。Dyson Canvas 应只存 `recipeId`，端口在渲染层派生。

7. **连线校验是原方案里最需要坚持的一条，而参考项目全都没做。** Graph-Calc 的 `onConnect` 是裸的 `addEdge(params, eds)`，零校验。这是本次调研发现的最大反面案例。

8. **许可证状况比原文档判断的更清晰，也更危险。** 0fuz/dsp-calc 确为 MIT（GitHub 报 `NOASSERTION` 是因为 LICENSE 尾部附加了图标条款）；Graph-Calc 与 DSP Helper **确认零 LICENSE**，只能作设计研究；dsp-calct 是 `DSPCalculator/dsp-calc` 的 fork，木兰 PSL 2.0 要求保留上游版权人。

9. **画布与计算必须彻底解耦，且求解结果永不落盘。** Graph-Calc 的 `stripSolveData()` 是正确做法；求解结果以 `nodeFlows / edgeFlows / problemEdgeIds` 三个映射回填画布，这个契约值得直接采用。

10. **LP 的松弛变量必须受游戏机制约束，不能默认「万物可买可扔」。** 可外购集合 = 被 `flags=['mining']` 配方产出的 18 个物品；可处置集合 = 带 `fuel` 字段的 27 个物品，**但必须按燃料类型分派设施**：21 项 chemical 进火电站、1 项 nuclear 进聚变站、2 项 antimatter 进人造恒星、2 项透镜属射线接收站消耗品、1 项满电池靠能源交换站放电。其余物品的松弛列必须置零，否则模型会给出物理上无法执行的解（§4.8）。

11. **目标函数用字典序，不用加权求和。** 同一模型下三组权重给出两种不同方案，且没有任何游戏内依据能判定哪种权重正确；字典序（先保供 → 再省料 → 最后省电）把优先级显式化，与量纲无关（§4.8.4）。

12. **自研 LP 求解器是候选方案，尚未成为锁定选型。** Python 原型已与 GLPK 5.0 在 8 个模型上逐一对照通过（§4.7），但 **TypeScript 正式实现尚未编写、更未验证**。在 TS 版本通过同一套用例之前，不得把「自研」写进技术决策。

## 2. 逐项目源码阅读记录

### 2.1 Graph-Calc（画布参考，P0）

#### 2.1.1 整体架构

前后端分离。前端 `React 19.2.4 + reactflow 11.11.4 + zustand 5.0.11 + elkjs ^0.12.0 + fengari-web(Lua 运行时)` `[源码确认]`（`frontend/package.json:13-22`）。后端为 .NET（`graphcalc.sln`），承担求解与项目持久化。

**关键发现：Zustand store 里没有 nodes / edges。** `useGraphStore` 只管理项目级*定义*（categories / items / tags / recipeTags / recipes / blueprints / modules），画布节点由 `App.tsx` 的 `useNodesState` / `useEdgesState` 持有，按 graph 维度单独持久化到后端 `[源码确认]`（`store/graphStore.ts:206-647`）。

这是一个重要的分层决策：**「项目定义」与「画布状态」是两个生命周期不同的东西**。定义变更要跨图传播，画布状态只属于单张图。

#### 2.1.2 画布系统

| 能力 | 实现 | 证据 |
|---|---|---|
| 节点创建 | 侧栏点击或拖拽 → 弹配置框 → `handleNodeConfigConfirm()` 生成 `{type}-${Date.now()}` id | `App.tsx:710-770`, `771-835` |
| 节点删除 | `deleteKeyCode={["Backspace","Delete"]}` 由 React Flow 处理；右键菜单走 `handleDeleteNode()` 并**同时清理边** | `App.tsx:698-703`, `2155` |
| 节点复制 | `graphClipboard.ts` 完整实现：`createGraphClipboardPayload` → 序列化到系统剪贴板 → `parseGraphClipboardPayload` 严格校验 → `materializeGraphClipboardPayload` 重映射 id | `domain/graphClipboard.ts:123-280` |
| 拖动 / 缩放 / 平移 | React Flow 原生；`panOnDrag={[1,2]}`（中/右键平移）、`zoomOnScroll`、`selectionOnDrag` | `App.tsx:2150-2154` |
| 多选 | `multiSelectionKeyCode={["Control","Meta"]}` | `App.tsx:2154` |
| 端口 | 每个端口一个 `<Handle>`，id 约定 `input-${port.id}` / `output-${port.id}` | `nodes/RecipeNode.tsx:214-236` |

**关于连线校验的补充说明**：`RecipeNode.tsx:219` 里有 `isConnectableStart={true}`，这只是一个 React Flow 的句柄开关，**不构成物品类型校验**。搜索全仓未发现 `isValidConnection`。因此「连接错误不会静默进入引擎」这一条，Graph-Calc **不满足**。

#### 2.1.3 自动布局（ELK.js）

`layoutGraph(nodes, edges, preset)` `[源码确认]`（`graphLayout.ts:84-116`）：

```ts
const graph = await elk.layout({
  id: "root",
  layoutOptions: getLayoutOptions(preset),
  children: nodes.map(n => ({ id: n.id, width: n.width ?? 240, height: n.height ?? 150 })),
  edges:   edges.map(e => ({ id: e.id, sources: [e.source], targets: [e.target] }))
});
return nodes.map(n => positions.has(n.id) ? { ...n, position: positions.get(n.id)! } : n);
```

三点观察：

- **只传 `id + 宽高`，完全没传 ports。** 因此没有 `elk.portConstraints`，端口顺序与连线走向不受约束，交叉最小化只看拓扑。若 Dyson Canvas 要求端口对齐，必须显式传入 `ports: [{id, width, height}]` 与 `elk.portConstraints: "FIXED_SIDE"`。
- **反向映射只改 `position`，其余字段原样展开**，所以「自动布局后保留节点信息」是天然成立的 —— 不需要额外序列化。
- **布局可撤销**：`handleApplyLayout()` 先存旧位置，布局后 `fitView`，并在通知里提供撤销动作 `[源码确认]`（`App.tsx:1533-1560`）。这个细节值得直接借鉴。

#### 2.1.4 节点系统与「失效连接」

`RecipeNode` 的 `data` 里冗余存了 `inputs: Port[]` / `outputs: Port[]`（含 `amountPerCycle`、`probability`）。这正是它必须写 `propagateProjectDataToNodes()` 的原因。

**Ghost Port 机制**（值得借鉴的正面设计）`[源码确认]`（`RecipeNode.tsx:115-150`、`projectPropagation.ts:135-144`）：配方变更后，若某端口消失但仍有连线接着，该端口不删除，而是降级为 `ghostInputs/ghostOutputs`，渲染成带 `Removed: xxx` 标签的禁用 Handle，边保留。

```ts
const ghostInputs = [...(node.data.ghostInputs ?? []), ...(node.data.inputs ?? [])]
  .filter(port => !inputs.some(cur => cur.id === port.id)          // 新配方已无此端口
              && edges.some(e => e.target === node.id
                            && e.targetHandle === `input-${port.id}`));  // 但仍有边连着
```

这比「静默删边」好得多：用户能看到「我原来的管线断了」，而不是发现数据莫名消失。但**代价**是节点数据结构复杂化，且 `propagate` 效果依赖 `nodes` 与 `setNodes`，存在潜在重入风险（代码用 `changedNodeIds.length > 0` 与 `effectiveFingerprint` 双重短路来规避）。

#### 2.1.5 状态管理与持久化

- Store 带 `schemaVersion: 7` 与单调递增的 `projectRevision` `[源码确认]`（`graphStore.ts:119-135`）。`projectRevision` 是**跨图失效传播的枢纽**：节点只要存的 revision 不等于当前的，就重算。
- 自动保存：300 ms 防抖 + 单飞行中的 Promise + pending 队列，且 `flushStoreSave()` 递归排空 `[源码确认]`（`graphStore.ts:148-187`）。这是一个可直接照抄的稳健模式。
- **所有破坏性变更前置 `window.confirm()`**（`confirmGraphImpact`），例如「删除物品会让所有图中引用它的节点失效」`[源码确认]`（`graphStore.ts:137-138`）。
- 持久化走 REST（`/projects/{id}/graphs/{gid}/save`），只有本地工作区用 `localStorage`，**没有 IndexedDB** `[源码确认]`（`api/persistence.ts`）。

#### 2.1.6 求解接口契约（最值得借鉴的部分）

前端拿到的不是一堆数字，而是**按节点/边 id 索引的流量映射** `[源码确认]`（`api/solve.ts:10-39`）：

```ts
type NodeFlowData  = { machineCount?, recipeRuns?, inputFlows, outputFlows, totalInput, totalOutput };
type EdgeFlowData  = { flows: Record<itemId, number>, totalFlow: number };
type SolveResponse = { status, machineCounts, flowsPerSecond, bottlenecks,
                       nodeFlows, edgeFlows, problemEdgeIds, warnings };
```

`problemEdgeIds` 单独列出「流量不匹配或零流」的边，直接驱动画布高亮。**这个契约应当成为 Dyson Canvas 的求解结果标准**，因为它把「计算」和「渲染」解耦成纯数据。

回填方式：`solveResult` 变化时用 effect 把 `solveData` 注入每个 node，把 `{flows, totalFlow, isProblem}` 注入每条 edge 并设 `label`；持久化前 `stripSolveData()` 剥离 `[源码确认]`（`App.tsx:598-638`、`:108`）。

### 2.2 DSP Sphere Program Helper（数据模型参考，P0）

#### 2.2.1 数据模型

`src/data/schema.ts` 定义了完整的归一化契约 `[源码确认]`：

```ts
Recipe  { id, name, time, in: RecipeItem[], out: RecipeItem[], producers: string[],
          flags: ('mining'|'technology'|'locked')[], cost? }
Machine { id, name, speed, usageKW, drainKW, modules, powerType: 'electric'|'none' }
Proliferator { id, name, tier, productivity, speed, consumption, sprays, mode }
Item    { id, name, category, row, stack }
```

**关键设计**：`in`/`out` 从 FactorioLab 的 `{itemId: count}` 映射转为**有序数组** `{id, amount}[]`，理由是「stable rendering」`[仅文档推断]`（`docs/data-pipeline.md:43-44`）。这个理由站得住：对象键序在 JS 中不保证插入序，端口渲染会抖动。

`payload` 的 `Proliferator` 把 DSP 的两种喷涂模式拆成 `mode: 'products'|'speed'` + 三个独立系数，比 DSL 式的「等级」表达更通用。

#### 2.2.2 递归求解器（重点核对原文的「visited 集合」判断）

原文判断：「使用 visited 集合检测循环，并将循环节点作为原料叶节点处理」。**源码确认成立，但有一处关键细节原文未提及**：

```ts
// solver.ts:83-90
if (!recipe) return leaf(true);
if (visited.has(itemId)) return leaf(true);   // 环 -> 当作原料
...
visited = new Set(visited);                   // ← 复制，不是共享
visited.add(itemId);
```

`visited` 是**按路径复制**的（`new Set(visited)`），不是全局共享集合。这很重要：若用全局集合，钻石型 DAG（两条支路共享同一中间产物）会被误判为环；路径复制则不会。案例 C 的可加性验证（`Plan(A+B) == Plan(A)+Plan(B)`，误差 0）从行为侧印证了这一点。

计算公式 `[源码确认]`（`solver.ts:94-110`）：

```
speed        = machine.speed × fx.speedMultiplier
resultAmount = recipe.out[item].amount × fx.outputMultiplier
craftsPerSec = ratePerSecond / resultAmount
timePerCraft = recipe.time / speed
machinesNeeded = craftsPerSec × timePerCraft
powerKW        = machinesNeeded × machine.usageKW × fx.powerMultiplier
```

注意 **`machinesNeeded` 不做向上取整**，保持分数。整套实现里没有任何 `Math.ceil`。这与 dsp-production-chain 形成鲜明对比。

**功耗只算 `usage`，不算 `drain`**，待机功耗完全缺失。FactorioLab 的数据集里 `flags: ['inactiveDrain']` 明确提示这是需要单独建模的机制。

**整数比例工具** `[源码确认]`（`solver.ts:138-233`）：`findDenominator()` 遍历 q ∈ [1,10000] 找能让 `v×q` 接近整数的最小分母（`eps=0.001` 且要求取整后**非零**），再 LCM 汇总、GCD 约分。`computeNodeMachineRatios()` 输出「每条产线在最小整数比下的台数」，`MAX_INTEGER_RATIO = 200` 超限则返回 null 不显示。这是一个很实用的展示层工具：玩家真正需要的是「3:2:1 的比例」，而不是 0.3333 台。

#### 2.3.1 求解主体

`solve(item, rate, depth, anc, noSpray)` `[源码确认]`（`index.html:252-309`）：

```js
if (rate <= 1e-9) return null;
if (depth > 16)   { /* loop 节点 */ }
DEM[item] = (DEM[item]||0) + rate;          // 全程需求累加
if (anc.has(item)) { /* loop 节点 */ }
if (CUT.has(item)) { /* cutoff 节点 */ }
const rec = await askRecipes(item, rate);    // 多配方时弹窗让用户选
...
const per = (oq/t) * spd * (1+ps) * (1+pp);
const cntE = rate/per, cnt = Math.ceil(cntE - 1e-9), act = cnt*per;
for (const k in rec.out) if (k !== item) BAL[k] += act*(rec.out[k]/oq);   // 副产品平衡
const mult = $('m_prop').value === 'exact' ? cntE : cnt;                  // ← 取整传播开关
for (const k in rec.in) {
  const need = rec.in[k]/t * spd * (1+ps) * mult;
  solve(k, need, depth+1, a2, noSpray);
}
```

五个可直接借鉴的点：

1. **`Math.ceil(x - 1e-9)`**：向上取整前的 epsilon 守卫。没有它，`2.0000000001` 会变成 3 台。
2. **`DEM` / `BAL` 双向累加**：`DEM` 记总需求，`BAL` 记副产品总产出，`net = BAL - DEM` 就是净剩余。这是**副产品诊断的最小实现**。
3. **`anc` 路径集**：`new Set(anc)` 同样是路径复制。
4. **`mult` 双策略**：`exact` 用理论台数、`rounded` 用取整后台数——把「取整是否传播」做成用户可见的选项。
5. **多配方时同步询问用户**（`askRecipes` 返回 Promise），并记忆到 `CHOSEN`，避免每次重算都弹窗。

#### 2.3.2 分馏塔的独立模型（值得注意的深度）

`frac(item, rate, depth, noSpray)` `[源码确认]`（`index.html:333-359`）对重氢分馏单独建模，提供三种口径：

```js
if (model === 'dataset') { count = Math.ceil(rate/0.01 - 1e-9); ... }        // FactorioLab 口径：每台 0.01/s
else if (model === 'belt') { count = Math.ceil(rate/(F*pct) - 1e-9); ... }   // 线性近似
else {                                                                        // 循环带几何衰减
  lanes = Math.max(1, Math.ceil(rate/(F*0.6)));
  count = Math.ceil(Math.log(1 - (rate/lanes)/F) / Math.log(1-pct) - 1e-9);
  loop  = F*lanes; act = F*lanes*(1 - Math.pow(1-pct, count));
}
```

几何衰减模型来自「循环传送带上每经过一台分馏塔，剩余氢按 `1-pct` 衰减」，是可解析的等比数列。这说明**某些配方需要专用模型，通用公式覆盖不了**。Dyson Canvas 的引擎需要预留「特殊配方处理器」注册点。

#### 2.3.3 诊断

`bottleneck()` `[源码确认]`（`index.html:592-615`）输出三类诊断：


#### 2.4.1 矩阵求解实现（逐行核对）

**① 自由度对齐 —— 强制方阵**


#### 2.6.1 混合算法的真实实现

README 声称「提取循环关键物品，仅对不得不参与线性规划的物品做 LP，其余递归」`[仅文档推断]`。阅读 `src/global_state.jsx` 后**确认属实** `[源码确认]`：

**① 拓扑剥离 + 关键物品识别**（`:325-395` `#init_item_list()`）：

```js
while (1) {
  // 反复删除出度或入度为 0 的节点，得到低→高的物品序
  ...
  if (Object.keys(product_graph).length <= 0) break;
  // 卡住时（剩余节点构成强连通核心），取「出入度之和最大」的节点为关键物品
  for (var this_item in product_graph) {
    count = Object.keys(product_graph[this_item]["原料"]).length
          + Object.keys(product_graph[this_item]["可生产"]).length;
    if (count > key_item["count"]) { key_item = {...}; }
  }
  key_item_list.push(key_item["name"]);
}
```

**这是本次调研中最优雅的一个启发式**：Kahn 拓扑排序做到卡住，剩下的必然是含环的核心；在核心里挑度数最大的物品作为「循环关键物品」切开。不需要 SCC 算法，却能达到类似效果。

**② 成本动态规划**（`:404-460` `#get_item_price()`）：沿拓扑序，把关键物品 / 矿化物品 / 多来源物品的成本置 0 作为边界，逐级累加「原料成本 + 建筑成本 + 占地 + 耗电 × 权重」。得到每个物品的 `累计成本`，作为 LP 的目标系数。

**③ 线性规划**（`:692-746`）：`javascript-lp-solver`，`optimize: 'cost'`，约束 `{min: demand}`，变量为配方，系数由 `item_graph[item]["原料"]` 与副产物项合成。显式处理 `feasible === false`（无解）与 `bounded === false`（无界）。

**结论**：这是六个项目里唯一实现了「成本驱动的多配方择优」的，也是唯一显式处理「无解 / 无界」的。但它的成本权重（占地、电力、建筑成本）是**硬编码的偏好权重**，不是游戏内真实资源成本。

### 4.2 案例 A：基础递归链

目标电磁矩阵 1/s，`assembling-machine-3` / `arc-smelter` / `matrix-lab`，无增产剂。

手算基准与求解器结果**完全一致**（偏差 `0.00e+00`）：

| 建筑 | 手算 | 求解器 |
|---|---|---|
| matrix-lab | 3.000000 | 3.000000 |
| assembling-machine-3 | 0.666667 | 0.666667 |
| arc-smelter | 3.500000 | 3.500000 |
| 铁矿石 | 2.000000/s | 2.000000/s |
| 铜矿石 | 1.000000/s | 1.000000/s |
| 总功耗 | 3420 kW | 3420 kW |

**最重要的产出是「取整传播」的实测**：同一方案在 `rounded` 策略下，`arc-smelter` 从 **3.50 台膨胀到 10.50 台**（+200%），铁矿石从 **2.00/s 膨胀到 6.33/s**（+217%），铜矿石从 1.00/s 到 4.00/s。

膨胀机理：0.3333 台的制造台向上取整为 1 台，倍率 3.0，把上游需求整体放大 3 倍；再在下游熔炉处二次取整，层层复利。

**结论**：`exact` 必须作为默认；`rounded` 若提供，必须在 UI 上明示「这是按实际产能层层富余的保守备料口径，不是精确值」，且**不得作为计算引擎的内部中间状态**。

### 4.3 案例 B：卡西米尔晶体

目标 1/s，展开 9 个制造层，`assembling-machine-3` 5.3333、`chemical-plant` 16.5、`arc-smelter` 16、`oil-refinery` 13，制造设备合计 50.8333 台（向上取整 52 台），功耗 35.88 MW，原料 6 种。全部与手算一致。

**配方切换对比**（同一目标 1/s）：

| 配方组合 | 设备(整) | 功耗(MW) | 原料种类 |
|---|---|---|---|
| 常规石墨烯 + 常规卡西米尔 | 52 | 35.88 | 6 |
| 高级卡西米尔 + 常规石墨烯 | 17 | 11.16 | 6 |
| 常规卡西米尔 + 高级石墨烯 | 40 | 29.04 | 6 |
| 高级卡西米尔 + 高级石墨烯 | **5** | **4.32** | 3 |

**52 台 → 5 台，10 倍差距。** 这不是调参，是配方路线的结构性差异（高级卡西米尔用光栅晶体替代整条钛晶支链；高级石墨烯用可燃冰一步替代高能石墨+硫酸支链）。这条数据直接说明：**「多配方择优」不是锦上添花，而是这个游戏规划工具的核心价值**。原方案把它放到 P6/P1，需要上调优先级。

**B.6 刻意失败的一项**：树模型把氢气 12/s 全部记为外购，同时又从等离子精炼副产 3.25/s 氢记入净流量，两者矛盾，物料守恒校验偏差恰好 `+3.25`。这不是实现 bug，是递归范式的固有局限——直接引出案例 D。

### 4.4 案例 C：多目标共享

目标电磁矩阵 1/s + 处理器 1/s。脚本从数据自动算出共享物品 5 个（`circuit-board` / `copper-ingot` / `copper-ore` / `iron-ingot` / `iron-ore`），非人工指定。

**线性可加性硬校验通过**（全部偏差 `+0.0e+00`）：

| 建筑 | 分别求解之和 | 合并求解 |
|---|---|---|
| Arc Smelter | 16.500000 | 16.500000 |
| Assembling Machine Mk.III | 6.000000 | 6.000000 |
| Matrix Lab | 3.000000 | 3.000000 |

共享物品确实合并到单条产线：`circuit-board` 两目标分别 1.0 + 2.0，合并后总消费 3.0（单条产线 1.0 台而非 2 台）。

**但结构重复依然存在**：合并后的树里 `copper-ingot` 出现 4 次、`copper-ore` 4 次、`iron-ore` 3 次、`circuit-board` 2 次、`iron-ingot` 2 次——共 10 个多余节点。

### 4.5 案例 D：氢气循环（矩阵层核心证据）

#### D.1 循环存在性 —— 用 SCC 证明，不假设

> **v2 修订说明**：本节初版把两个 SCC 都笼统写成「循环」，并据此下了「唯一循环」的结论。经复核，两个分量性质不同，且结论需要绑定口径。以下为修订后版本。

物品依赖图（边 `u→v` 表示「产 v 需耗 u」）：**174 节点 / 444 边**（主口径）。
（v3 修正：v2 写的 110 漏计了纯输出节点，详见 §4.10。）Tarjan 结果：**2 个强连通分量**，但只有一个是物料生产循环。

**分量 1：`{hydrogen, refined-oil}` —— 物料生产循环（纳入）**

```
hydrogen    -> hydrogen        x-ray-cracking 自环：耗 2 产 3，净 +1
refined-oil -> refined-oil     reforming-refine 自环：耗 2 产 3，净 +1
hydrogen    -> refined-oil     reforming-refine：耗 H2 产 RO
refined-oil -> hydrogen        x-ray-cracking：耗 RO 产 H2
```

判定依据：这些配方**改变物料构成**——原油变成氢气与精炼油，精炼油加氢变成高能石墨。净转化不为零。

**分量 2：`{accumulator, accumulator-full}` —— 储能充放电往返（不纳入）**

| 配方 | 输入 | 输出 | 建筑 | 工时 |
|---|---|---|---|---|
| `accumulator` | 晶硅 ×3 + 铁锭 ×6 + 超磁环 ×1 | 蓄电池 ×1 | 制造台 | 3s |
| `accumulator-full` | 蓄电池 ×1 | 满电池 ×1 | **能源交换站** | 10s |
| `accumulator-discharge` | 满电池 ×1 | 蓄电池 ×1 | **能源交换站** | 10s |

`accumulator-full` 与 `accumulator-discharge` 互为逆过程（`in(r1)==out(r2)` 且 `out(r1)==in(r2)`，按 `{item: amount}` 精确相等），净物料转化恒为零。它表达的是「给电池充电 / 放电」这一**能量状态切换**，不是生产。

**为什么第一版不纳入**

1. **它不产生净物料流。** 往返一次蓄电池数量不变，任何把它纳入物料平衡的写法都会引入一组恒等于零的变量，只会增加退化风险，不提供信息。
2. **它不是持续生产环节。** `accumulator-full` 只有两个下游用途：放电（回环，净零）与建造轨道采集器（每台 20 个，一次性建造消耗，不是产线吞吐）。
3. **它的成本不在物料侧。** 真正需要建模的是「充放电损耗与功率」，那属于能量模型，不属于物料平衡模型。硬塞进第一版会让数据结构背上用不上的字段。

**第一版的处理方式**：把 `accumulator-discharge`、`accumulator-full` 排除在求解配方集之外（可按 `producers: ['energy-exchanger']` 过滤，或直接白名单排除这两条 id），并在数据层保留它们以便将来做能量模块。**这是一个显式决策，需要在 P1 的数据模型里写成 `excludedByDefault` 标记，而不是靠某条隐式规则。**

#### D.1.1 口径敏感性 —— 「唯一」必须带条件

同一结论在不同过滤规则下并不都成立。实测四组口径（`python3 stats.py --regimes`）：

| 口径 | 配方数 | 图规模 | SCC | 物料生产循环 |
|---|---:|---|---:|---|
| R0 全量（含 307 条 `technology` 研究配方） | 496 | **481** / 1253 | 2 | 1 |
| **R1 剔除 `technology`（本报告主口径）** | **189** | **174 / 444** | **2** | **1** |
| R2 每物品仅保留首选配方 + 全部 `mining` | 173 | **172** / 424 | **0** | **0** |
| R3 剔除 `energy-exchanger` 配方（充放电） | 187 | **174** / 442 | 1 | 1 |

**R2 的结果最值得注意**：每物品只保留一条首选配方时，循环在图上**完全消失**。原因是在该口径下 `refined-oil` 只有 `plasma-refining`、`hydrogen` 只有 `gas-giant`（采集），二者不构成互相依赖。

这意味着：**「单主配方」不是「简化」，而是把循环问题从视野里删掉。** DSP Helper 正是采用单主配方策略，所以它的求解器永远遇不到循环——不是因为它处理得好，而是因为它看不见。这条结论直接支撑了 §5.1「多配方能力必须一开始就有」。

因此本报告对该结论的完整表述是：

> 在 DSP `0.10.29.21950` 的 FactorioLab 数据集上，剔除 307 条 `technology` 研究配方后，对 189 条生产配方构图，**物料生产循环恰好 1 个**（`{hydrogen, refined-oil}`），另有 **1 个储能充放电往返环**（`{accumulator, accumulator-full}`，不纳入求解器）。超出该数据版本或该过滤口径不作保证。

它把原方案里「P4 复杂生产网络」的风险从「未知规模的通用求解器」压缩成「一个 2 变量的子系统 + 一次显式排除」。

#### D.2 方阵求解（复现 0fuz 的方法）

变量 = 等离子精炼 / X 射线裂解；平衡物品 = 精炼油 / 氢气；需求 = 6.5 / 12。

| 物品 | 等离子精炼 | X 射线裂解 | b |
|---|---:|---:|---:|
| Refined Oil | +2 | −1 | 6.5 |
| Hydrogen | +1 | +1 | 12 |

`rank(A)=2`，唯一解 `x = (37/6, 35/6) = (6.166667, 5.833333)`，全部非负。

派生量校验（可人工复算）：原油 12.3333/s；高能石墨产 5.8333/s 而需求 5/s → **富余 0.8333/s** 无处安放。

**这就是方阵模型的固有缺口**：它只能挑 2 个物品做等式，第 3 个物品的净流量变成隐性废弃物。

#### D.3 松弛变量 + LP

> **v2 修订说明**：本节是**上界模型**——为先把数学结构讲清楚，暂时假设所有物品都能无限外购、无限放空。这个假设在游戏里不成立。**真实可执行的版本见 §4.8**，那里由数据决定哪些物品可外购（`mining` 配方产出）、哪些可放空（带 `fuel` 字段），并用字典序目标替代加权求和。

模型：

```
min c·x   s.t.  A_net·x + s⁺ − s⁻ = b,   x, s⁺, s⁻ ≥ 0
  s⁺ = 外购量（不足时从外部补齐）
  s⁻ = 放空量（富余时排掉）
```

结果（状态 `optimal`，7 次迭代）：

| 配方 | 最优速率 |
|---|---:|
| plasma-refining | 6.166667 |
| x-ray-cracking | 5.833333 |
| reforming-refine | 0.000000 |

| 物品 | 需求 | 外购 s⁺ | 放空 s⁻ |
|---|---:|---:|---:|
| Refined Oil | 6.500 | 0 | 0 |
| Hydrogen | 12.000 | 0 | 0 |
| Energetic Graphite | 5.000 | 0 | **0.8333** |

与方阵解一致（`p=6.1667`），但**把富余显式化为「放空 0.8333/s」**，而不是让它悄悄消失。守恒逐项精确通过。

所用权重为 `(100, 10, 1)`，即「外购远重于放空、放空重于运行成本」。**这三档数值没有游戏内依据**，只是为了在演示中体现优先级；§4.8.4 会证明换一组权重就会换一个答案。

#### D.4 与树模型的量化对照

| 口径 | 原油/s | 氢外购/s | 回路产氢/s | 净氢缺口/s |
|---|---:|---:|---:|---:|
| 递归树（氢取气态巨星） | 6.5000 | 12.0000 | 3.2500（未计入） | 12.0000 |
| 矩阵 + 松弛 LP | 12.3333 | 0.0000 | 12.0000 | 0.0000 |

树模型**高估氢气外购 12/s（100%）**，同时**低估原油 5.83/s**。这不是精度问题，是范式问题。而且矩阵解并非「更省」——它是用更多原油换氢气。**工具应当把这个取舍呈现给玩家，而不是替他默认选一个。**

### 4.7 案例 F：自研 LP 求解器与 GLPK 的对照验证

> **本节为 v2 新增。** 初版曾经把「自研单纯形」直接写进技术选型表，理由是「Python 原型跑通」。这是不充分的：Python 原型通过不代表 TypeScript 正式实现已经验证。本节补上第三方求解器对照，并据此把该选型降级为**候选**。

#### F.1 方法

- **对照求解器**：GLPK 5.0，从 `ftp.gnu.org/gnu/glpk/glpk-5.0.tar.gz` 下载源码，本机 `configure && make && make install` 编译到 `/tmp/glpk`。选它是因为 **FactorioLab 的生产求解器就是 GLPK 的 WASM 移植（`glpk-ts`）**——与 GLPK 一致，等价于与参考项目的求解内核一致。
- **同一份模型**：两侧都从同一个 `LPProblem` 数据结构生成，一侧直接调 `linalg.simplex_min`，另一侧写成 CPLEX LP 格式喂给 `glpsol`。杜绝人工转录误差。
- **独立可行性校验**：把任一方给出的 `x` 代回原模型，检查等式残差与非负性。**这一步不依赖任何求解器**，即使两边同时错也能发现。

#### F.2 八个模型的对照结果

| 场景 | 自实现 | GLPK | 目标值(自) | 目标值(GLPK) | 判定 |
|---|---|---|---:|---:|---|
| F1 可行·唯一最优 | optimal | optimal | −12.000000 | −12.000000 | PASS |
| F2 不可行 | infeasible | infeasible | — | — | PASS |
| F3 无界 | unbounded | unbounded | — | — | PASS |
| F4 退化（Beale 循环示例） | optimal | optimal | −0.050000 | −0.050000 | PASS |
| F5 多解·无穷多最优 | optimal | optimal | 0.000000 | 0.000000 | PASS |
| F6a DSP·氢气回路（含松弛） | optimal | optimal | 20.666667 | 20.666670 | PASS |
| F6b DSP·多配方择优 | optimal | optimal | 3.000000 | 3.000000 | PASS |
| F6c DSP·无松弛不可行 | infeasible | infeasible | — | — | PASS |

容差说明：GLPK 的 `-o` 文本解只有 6 位小数，因此目标值容差取 `1e-5`、解向量与可行性容差取 `1e-4`，而不是 `1e-9`。这不是精度妥协的借口，而是把**输出格式的量化误差**与**算法误差**区分开。

F1（可行且有界）与 F6b（唯一最优的 DSP 场景）另做了**解向量逐分量比对**，差异均在 `1e-6` 以内。F5 属无穷多最优，只比目标值，两侧都给出 0，符合预期。

**这 8 个模型不是由同一种方法验证的**（v4 更正）。按模型类型分派独立基准，逐项如下：

| 模型 | 独立验证方法 | 具体结果 |
|---|---|---|
| F1 / F4 / F5 / F6a / F6b | 顶点枚举（`enumerate_optimum`） | 5 个模型各自枚举出 4 / 19 / 2 / 10 / 4 个可行极点，最小 z 与 ORACLE 相等 |
| F2 / F6c | RREF 一致性 + 基可行解存在性 | F2 检出 `0 = 1` 型矛盾；F6c 一致但不存在基可行解（`no_bfs`） |
| F3 | **射线证书**（`verify_ray_certificate`） | `x0=(0,0)`、`d=(1,1)`，六条条件逐项成立；枚举器只能给出极点 z=0，**不足以判定无界** |

> 无界问题同样有可行极点，所以顶点枚举**不能**用来证明无界，只能给出「极点上最小的 z」。把「枚举到极点」当成「有界」或把「枚举不到」当成「不可行」，都是把方法用错了地方。

#### F.2.1 无界证书的修正（v4）

v3 的 `has_negative_ray()` 用「存在列 j 使 `c_j < 0` 且 `A[:,j] <= 0`」作为无界证据。**这条推理在等式约束下是错的**：可行方向必须满足 `A·d = 0`，而不是 `A·d <= 0`。

反例（本轮审阅给出，已复现）：

```
min -x      s.t.  -x = -1,  x >= 0        # 唯一解 x=1, z=-1，显然有界
```

列 x 的成本 `-1 < 0`、系数 `-1 <= 0`，v3 判据返回 `True`；但沿 `e_x` 走一步就破坏等式 `-x=-1`。自实现单纯形与 GLPK 都正确返回 `optimal / z=-1`，只有那个「证书」是错的。

修正后的证书是 `(x0, d)` 六条条件的合取，全部用 `Fraction` 精确算术逐项验证：

| # | 条件 | 作用 |
|---|---|---|
| 1 | `A·x0 = b` | x0 是可行点 |
| 2 | `x0 >= 0` | 满足非负约束 |
| 3 | **`A·d = 0`** | 方向保持等式（v3 漏掉的就是这一条） |
| 4 | `d >= 0` | 方向不离开非负象限 |
| 5 | `d != 0` | 否则不是方向 |
| 6 | `c·d < 0` | 目标沿方向严格下降 |

1–6 成立时 `x(t) = x0 + t·d` 对任意 `t >= 0` 可行且 `z(t) → -∞`。实现里还用 `t ∈ {0,1,10,1000}` 采样把这条推论验了一遍（防御 3/4 写错）。

**关键区分：只验证方向、不给可行点，不能宣称整个问题无界。** 不可行问题也可能存在下降方向——`min -x, -x = 1, x >= 0` 的列条件成立，但可行域为空，正确结论是 `infeasible` 而不是 `unbounded`。因此 `prove_unbounded()` 的顺序是「先验可行性，再验方向」：

```
第 1 步  min 0  s.t. A·x=b, x>=0      → infeasible 则直接返回 infeasible
第 2 步  min c·d s.t. A·d=0, Σd=1, d>=0
           infeasible          → 非负零空间只有零向量 ⇒ bounded
           optimal 且 c·d >= 0 → 无下降方向            ⇒ bounded
           optimal 且 c·d <  0 → 得到 d，交证书逐项复核 ⇒ unbounded
```

回归覆盖四类（`case_f` 的 F12–F15）：有界反例（旧判据误报）、真无界（F3 的 `x0,d`）、真无界但射线不是单位列（旧判据漏报）、方向存在但不可行（旧判据误判为无界）。

#### F.2.2 顶点枚举对冗余约束的处理（v4）

v3 的 `enumerate_optimum()` 按**原始约束行数 m** 选 m 列求基。遇到重复或线性相关的约束，它必然枚举不出任何基：

```
min x      s.t.  x = 1 ;  x = 1 ;  x >= 0
```

两行一列，没有 `C(1,2)` 这种组合 → 返回 `status="no_vertices", n_feasible=0`。而调用方把 `no_vertices` 当作「不可行」的证据 —— **一个正确答案为 x=1、z=1 的模型被判死**。

修正后的顺序：

1. 对增广矩阵 `[A|b]` 做 RREF，检出 `0 = c (c≠0)` 即判 `infeasible / rref_contradiction`；
2. 用贪心选出**线性无关的原始行**（`independent_rows()`），得到有效行秩 `r`，按 r 列枚举；
3. 一致但枚举不到基可行解时，才判 `infeasible / no_bfs`。

第 3 步不是「猜」：`{x >= 0 : A·x = b}` 非空 ⇒ 必存在基可行解（取支撑集最小的可行点，其正分量对应的列必线性无关）。所以「一致 + 无 BFS ⇒ 可行域为空」是有定理支撑的，而不是把「没枚举到」冒充成「不存在」。

**不支持的情形必须说「不知道」**：规模超限返回 `too_large`、空模型/行秩为 0 返回 `unsupported`，两者都**不得**被调用方计入「不可行」。回归 F19 专门守这条。

回归覆盖（`case_f` 的 F16–F19）：

| 用例 | 输入 | 期望 | v3 行为 |
|---|---|---|---|
| F16 重复约束但可行 | `x=1, x=1` | `has_vertices, z=1` | `no_vertices`（错） |
| F17 重复左端、右端矛盾 | `x=1, x=2` | `infeasible / rref_contradiction` | `no_vertices`（结论对、理由错） |
| F18 线性组合冗余 | `x=1, 2x=2` | `has_vertices, z=1` | `no_vertices`（错） |
| F19 枚举预算不足 | `max_bases=0` | `too_large`（结论未知） | 同为 `too_large`，但需断言不被当成不可行 |

#### F.3 对照过程中暴露的一个真实工程坑

首轮 F3（无界问题）两侧结论不一致：自实现报 `unbounded`，GLPK 报 `UNDEFINED`。

排查结果：**GLPK 的预解器（presolver）在判定无界时会返回 `UNDEFINED` 状态**，与「不可行」共用同一个状态码。加 `--nopresol` 后 stdout 明确输出 `LP HAS UNBOUNDED PRIMAL SOLUTION`，状态变为 `UNBOUNDED`。

这条要写进实现约束：**如果将来选 GLPK 系方案，必须关掉预解或读日志消歧，否则「无界」会被误判成「不可行」，两者对用户的含义完全不同**（一个是参数写错，一个是配方根本凑不出来）。

#### F.4 结论与边界

**已验证（Python 原型）**

- **在有 GLPK 的环境下**，与 GLPK 在 8 个模型上状态、目标值全部一致；无 GLPK 时该对照标记为 SKIP（不计入通过，也不影响其余判定）；
- 每个解都通过独立可行性校验；
- 覆盖了可行 / 不可行 / 无界 / 退化 / 多解 / 真实 DSP 场景六类；
- 8 个模型的**独立验证方法逐项标注**：5 个由顶点枚举、2 个由 RREF/基可行解判定、1 个由射线证书；没有「枚举器证明了全部」这种笼统说法；
- 无界证书与冗余约束各有一组会失败的反例回归（F12–F19），且这些断言经过故障注入验证（改坏后必须报错）。

**仍待验证（不得跳过）**

1. **TypeScript 正式实现尚未编写，更未验证。** 本案例只证明算法思路正确，不证明 TS 代码正确——位宽、除法精度、数组越界、大模型性能都未覆盖。
2. **规模边界未测。** 本案例最大模型 3 约束 × 9 变量；真实规划可能上百变量，未做性能与数值稳定性测试。
3. **未编译为 WMS/WASM 交付形态**，包体积与启动开销未知。

**因此技术选型降级为**：`LpBackend` 抽象接口（`solve(problem) → result`），默认候选为自研 TS 实现，**备选** `javascript-lp-solver`（dsp-calct 在用）与 `glpk-wasm`（FactorioLab 在用）。锁定条件：TS 版本在同一套 8 个模型上跑通并与 GLPK 对齐，**且通过 F12–F19 这 8 条证书/枚举回归**，才允许替换默认实现。

### 4.8 案例 G：循环边界处理 与 松弛变量的可执行性约束

> **本节为 v2 新增**，回答审核提出的第 2、3 项。

#### G.1 可外购 / 可放空 不是人为设定，而是数据决定

初版让所有物品都能被 `s⁺`（外购）和 `s⁻`（放空）自由调节，这会产生游戏里根本无法执行的解。正确做法是从数据里推出约束：

| 集合 | 判据 | 规模 | 依据 |
|---|---|---:|---|
| 可无限外购 | 被 `flags=['mining']` 的配方产出 | **18 项** | 矿脉/海洋/气态巨星/原油渗井可持续采集 |
| 可燃烧 · chemical | `fuel.types` 含 chemical 且建筑 `fuel_types` 接受 | **21 项** | 火电站 `thermal-power-plant` |
| 可燃烧 · nuclear | `fuel.types` 含 nuclear | **1 项** | 微型聚变发电站 |
| 可燃烧 · antimatter | `fuel.types` 含 antimatter | **2 项** | 人造恒星 |
| 被建筑消耗（非燃料） | 出现在建筑 `consumption` 中 | **2 项** | 射线接收站耗透镜 |
| 经配方转化 | 状态往返配方（满电池→蓄电池） | **1 项** | 能源交换站 |

> **v3 更正**：v2 把「带 `fuel` 字段」直接等同于「可以送进火力发电站烧掉」，这是**错误等价**。
> 实际约束写在建筑的 `machine` 区块里：`thermal-power-plant.fuelTypes = ["chemical"]`。
> 27 个 fuel 物品里只有 21 个是 chemical —— 另外 6 个是 1 个核燃料棒、2 个反物质燃料棒、
> 2 个透镜、1 个满蓄电池，它们各有专属设施，塞进火电站是游戏里做不到的。

本模型涉及的三个边界物品：

| 物品 | 可外购 | 可放空 | 说明 |
|---|:--:|---:|---|
| Refined Oil | 否 | 是（fuel=4.5） | 只能生产；富余可烧 |
| Hydrogen | **是** | 是（fuel=9） | 气态巨星可采；可烧 |
| Energetic Graphite | 否 | 是（fuel=6.75） | 只能生产；**可烧** |

其余物品（如硫酸、钛晶、卡西米尔晶体）既无 `mining` 配方也无 `fuel` 字段，松弛列必须置零。**它们在游戏里既买不到也扔不掉，产出过剩只会堵线。** 把这类物品也加上 `s⁻` 是失真的。

#### G.2 SCC 的边界：高能石墨为什么不在环内

用收缩图识别边界（`case_g` / `case_h` 自动计算）。**这里必须先说清口径**，因为 v2 与现行实现给出的是两个不同的数：

| 口径 | 环内配方 | 入边物品 | 出边物品 | 问题 |
|---|---|---:|---|---|
| v2「反查产出者」 | **9 条**：`gas-giant`、`gas-giant-hydrogen`、`graphene-advanced`、`ice-giant`、`ice-giant-hydrogen`、`mass-energy-storage`、`plasma-refining`、`reforming-refine`、`x-ray-cracking` | coal, critical-photon, crude-oil | antimatter, deuterium, energetic-graphite, graphene | 把 4 条 `mining` 采集配方与 2 条产物越界的配方也算成「环内生产列」，边界因此膨胀 |
| 现行（v3 起，规则 A/B） | **3 条**：`plasma-refining`、`reforming-refine`、`x-ray-cracking` | coal, crude-oil | energetic-graphite | 采集配方归入「外购通道」而非生产列；产物越界的配方显式排除并记录理由 |

**口径差异的来源**：v2 把「能产出 SCC 物品的全部配方」都算进环路（数据集里共有 8 条配方能产出氢气）。但 SCC 的定义域是**物品**，不是配方；把 `gas-giant` 这类采集配方放进来，等于把「从气态巨星抽氢」和「裂解原油产氢」当成同一层决策，而这正是 LP 要比较的两条路线。现行实现因此把配方分成三类：

- **生产列**（进矩阵）：规则 A「同时消耗并产出 SCC 物品」+ 规则 B「无采集来源物品的必要生产者」；
- **外购通道**（不进矩阵，进 `s⁺` 列）：`flags=['mining']` 的配方；
- **显式排除**（记录理由）：产物越界（`graphene-advanced` → 石墨烯、`mass-energy-storage` → 反物质）、状态往返（`accumulator-*`）。

**`energetic-graphite` 是出边物品，不在 SCC 内。** 它由 `x-ray-cracking` 产出，但消费者（`graphene`、`plastic`、`diamond`）都在环外。这带来一个必须显式处理的后果：

> 若只对 SCC 内部三个物品（RO/H2/EG）中的前两个建平衡行，EG 的产出就**没有归属**，会变成隐形废弃物。

#### G.3 高能石墨的三种处置方式

同一目标（RO 6.5/s、H2 12/s、EG 5/s），三种建模：

| 建模 | plasma | xray | 外购 H2 | 放空 EG | 结果说明 |
|---|---:|---:|---:|---:|---|
| M1 只解 SCC 内部（RO+H2 两行） | 6.1667 | 5.8333 | 0 | — | EG 产出 5.8333，需求 5，**差额 0.8333 无任何约束记录** |
| M2 EG 进全局平衡 + 允许焚烧 | 6.1667 | 5.8333 | 0 | **0.8333** | 可行；多余石墨烧掉 |
| M3 EG 进全局平衡 + 禁止焚烧 | 5.7500 | 5.0000 | **1.2500** | 0 | 可行；改为从气态巨星补氢 |

**三者都「算得出来」，但只有 M2 与 M3 是可执行的。** M1 的 0.8333 在界面上不会显示，玩家按它建厂会得到一堆无处的石墨。

M2 与 M3 是两条**真实可选**的路线：烧掉多余石墨，或者少裂解一点、从气态巨星补氢。选择取决于玩家有没有气态巨星、愿不愿意让产线多一个进口。**工具应当把这个取舍呈现出来，而不是替他默认一个。**

#### G.4 目标函数：字典序，而不是加权求和

模型的四类成本项与优先级：

| 优先级 | 目标 | 含义 | 为什么在这个位置 |
|---|---|---|---|
| ① | 最小化外购量 Σs⁺ | 依赖外部供应 | 外购意味着物流与矿点，是玩家最难扩展的约束 |
| ② | 最小化放空量 Σs⁻ | 浪费 | 放空只是损失，但不影响产线能否运转 |
| ③ | 最小化配方运行成本 Σc·x | 能耗/占地/建筑 | 在满足前两者后才有意义的优化 |

实现用**字典序（preemptive / sequential）**：先解①，把最优值作为等式约束锁死；再解②；最后解③。这样优先级严格，不依赖权重标定。

对照实验（同一模型，三种权重 + 字典序）：

| 目标函数 | 状态 | 外购 H2 | 放空合计 | 运行成本 |
|---|---|---:|---:|---:|
| (100, 10, 1) 外购≫放空≫运行 | optimal | 0.000 | 0.833 | 12.333 |
| (1, 1, 1) 三者等权 | optimal | 1.250 | 0.000 | 11.500 |
| (1, 100, 1) 放空被重罚 | optimal | 1.250 | 0.000 | 11.500 |
| **字典序 外购→放空→运行** | optimal | **0.000** | **0.833** | **12.333** |

三组权重给出**两种**不同方案。答案是「你认为一次外购抵几次放空」的函数，而这个问题在游戏机制里**没有客观答案**。加权法必须标定一个「100 倍惩罚」这种无依据的常数，字典序只需要说清楚业务顺序：「先保供、再省料、最后省电」。

字典序最终解经独立回代校验：RO 6.500000（需 6.5）、H2 12.000000（需 12）、EG 5.000000（需 5），全部 PASS。

#### G.5 结论

1. **松弛变量必须受策略约束**，策略由数据字段推出（`mining` / `fuel`），不能全局开放。
2. **SCC 的求解子图 = SCC ∪ 入边物品 ∪ 出边物品**，只解 SCC 内部会把边界的副产物变成隐形废弃物。
3. **目标函数用字典序**，优先级显式、与量纲无关；加权法的答案随权重漂移。

### 4.9 验证暴露的十三个工程问题

1. **净流量重复扣减**：首轮案例 A 的守恒校验爆出 `iron-ore` 净流量 -4 而预期 -2。原因是父节点已扣消费、叶节点又扣一次。**说明「守恒校验」必须从第一行代码就存在，否则这类错误会一直隐藏。**
2. **矿石语义**：首轮把 `iron-ore` 当无配方物品，实际它由 `iron-vein` 产出。修正后引入显式 `mining_policy`。
3. **取整传播的复利**：见 4.2，3.2 倍误差。
4. **树结构重复节点**：见 4.4，汇总对但结构错。
5. **方阵的隐性废弃物**：见 4.5，第 3 个物品的净流量被静默丢弃。
6. **GLPK 预解器把「无界」报成「UNDEFINED」**：见 4.7.3。若不加 `--nopresol`，无界与不可行共用状态码。这是选型阶段必须知道的实现细节。
7. **全局开放松弛会给出不可执行的解**：见 4.8.1。初版允许「硫酸倒掉」，而游戏里没有删除物品的操作。
8. **节点统计漏计纯输出物品**：见 §4.10。v2 报告的全部图规模数字都偏小。
9. **整数设备按机器合并取整会少算**：见 §4.11。案例 A 少 1 台、案例 C 少 1 台。
10. **迭代上限被冒充为「不可行」或「最优」**：见 §4.12。这是会把「没算完」说成结论的一类错误。
11. **等式约束下的「负射线」判据不成立**：见 §4.7.2.1。`A·d <= 0` 不能替代 `A·d = 0`；
    更危险的是「只验方向、不验可行点」——不可行问题也会被报成无界。
12. **顶点枚举没处理冗余约束**：见 §4.7.2.1。按原始行数选列，遇到 `x=1, x=1` 就枚举失败，
    而失败被当成「不可行」。**「没枚举到」不等于「不存在」。**
13. **环外副产物没有回供**：见 §4.13.5。需求只累计消耗、不抵扣副产，
    整张图会多出无人认领的物料，而 LP 自己的平衡行仍然通过。
    **局部守恒不能代替全局守恒。**

### 4.10 案例 I：图节点统计的修正（v3 新增）

> 本节记录一次**统计口径缺陷**，它不影响任何计算结论，但让 v2 报告里所有「图规模」数字都偏小。

#### I.1 缺陷

```python
# v2 的 build_item_graph
for o in r["out"]:
    for i in r["in"]:
        g.setdefault(i, set()).add(o)     # 只为「输入物品」建键
for o in list(g):                          # 遍历的仍是已存在的键
    g.setdefault(o, set())
```

第二段看似在补输出节点，但 `list(g)` 里的键全部来自第一段的输入侧，
因此**纯输出节点**（被生产、但从不作为输入被消耗的物品）永远拿不到键。

#### I.2 影响

| 口径 | v2 报告 | 实测（修正后） | 边数 |
|---|---:|---:|---:|
| R0 全量（含 technology） | 111 | **481** | 1253（不变） |
| R1 主口径（189 条配方） | 110 | **174** | 444（不变） |
| R2 每物品首选配方 | 104 | **172** | 424（不变） |
| R3 剔除充放电配方 | 109 | **174** | 442（不变） |

边数完全不变 —— 因为边只由 `in → out` 对产生，与节点是否建键无关。
这个特征可以用来区分「节点统计错」与「图结构错」：**只有节点数变、边数不变，就是计数问题。**

#### I.3 修复

1. 构图时**先为 `out` 与 `in` 两侧都建键**，再连边。
2. 新增 `count_graph()` 作为唯一计数入口，并内置断言：
   凡出现在任何邻接表里的目标，必须也是一个键。断言失败即抛异常，不再静默少算。
3. 新增 `case_i_graph_stats.py`：合成用例覆盖「纯输出节点」「无输入配方」「链式终端」，
   并内置一条「构造漏键图，断言必须抛异常」的反向测试。

#### I.4 结论是否受影响

**不受影响。** SCC 分类、循环存在性、唯一物料循环的口径结论都只依赖边的拓扑，
而边数在修正前后完全一致。§4.5.1 的四口径对照表已按新数字更新，结论文字未改。

### 4.11 整数设备口径（v3 新增）

#### J.1 缺陷

v2 的 `Plan.machines` 是 `Dict[machine_id, float]`，`machines_ceil()` 直接对这个汇总值取整：

```python
return {k: int(math.ceil(v - 1e-9)) for k, v in self.machines.items()}
```

问题在于**不同配方不能用同一台机器同时生产**。案例 A 里电路板与磁线圈各需 1/3 台制造台，
汇总后 2/3 取整得 1，而实际必须各建 1 台、共 2 台。

#### J.2 修正

`Plan` 增加 `machine_groups: Dict[(recipe, machine, config), float]`，
累加时就按「配方 × 机器 × 运行配置（增产剂）」分组；`machines_ceil()` 在分组粒度取整后再按机器汇总。

| 场景 | 分组口径 | 按机器合并口径 | 差额 |
|---|---:|---:|---:|
| 案例 A（电磁矩阵 1/s） | **9 台** | 8 台 | 1 |
| 案例 C（电磁矩阵 + 处理器） | **27 台** | 26 台 | 1 |

差额恰好等于「存在两条各需不足 1 台的配方共用同一机型」的机器种类数。

#### J.3 表述要求

报告与界面必须把两个数字分开说：

- **理论台数**（小数）：用于描述产能占用，可加、可比较；
- **建设台数**（整数，按配方分组）：用于玩家实际建造，不可加。

把两者混为一谈（例如用理论台数乘以单价估算成本）会系统性低估。

### 4.12 迭代上限：第四种状态（v3 新增）

#### K.1 缺陷

`simplex_min(max_iter=N)` 在预算耗尽时返回内部状态 `"maxiter"`，但两个阶段都没有正确传递它：

```python
# 第一阶段
if st != "optimal":
    return {"status": "unbounded" if st == "unbounded" else "infeasible", ...}
    #                                                  ^^^^^^^^^^^ maxiter 落到这里
# 第二阶段
if st == "unbounded":
    return {...}
# 之后直接算出 x 并 return "optimal"                    # maxiter 落到这里
```

复现模型 `min x, s.t. x+y=1, x,y≥0`（真最优 0）：

| 预算 | v2 结果 | 应有结果 |
|---|---|---|
| `max_iter=1` | `infeasible`（错：问题明明可行） | `maxiter` |
| `max_iter=2` | `optimal, z=1`（错：真最优是 0） | `maxiter` 或 `optimal, z=0` |

#### K.2 修正

1. 新增第四种状态 `"maxiter"`，与 `optimal / infeasible / unbounded` 并列，且 `x`、`z` 一律为 `None`。
2. 两阶段任一命中都原样传出，附带 `phase` 与 `reason`。
3. **预算按枢轴次数计**，而不是循环次数 —— 最后一次进入循环只是「验证是否已最优」，它不改变解，不应消耗预算。
4. 判定改为不变量：**对任意预算，要么 `maxiter`，要么 `optimal` 且值确实最优**。案例 F 的 F7–F10 扫描预算 1..6 验证这一点。

#### K.3 为什么这条重要

「不可行」与「没算完」对用户的含义完全不同：前者让人去改配方，后者只需要调大预算。
把后者说成前者，会让用户在一个本来就可行的问题上反复试错。

### 4.13 案例 H：边界自动化（v3 新增）

#### H.1 v2 的问题

v2 的案例 G 打印了 SCC 边界，但**喂给 LP 的矩阵是手写的三行三列**，需求是 `DEMAND` 常量。
打印与求解之间没有任何程序连接 —— 也就是说「自动识别边界」这件事从未被验证。

#### H.2 现在的链路

```
目标产量 ─► 递归展开（遇到边界物品即停）─► 环外配方的实际速率 + 全部输入输出
                    │                              │
                    │                              ├─► 边界物品的消耗 gross_in
                    │                              └─► 边界物品的副产 gross_out
                    └─► 配方选择规则 A/B ─► 净流量矩阵 A
                                            b[i] = gross_in + 目标直接 − gross_out
```

配方入选规则（两条，都可独立复核）：

- **规则 A**：该配方**同时消耗并产出** SCC 物品（x-ray-cracking、reforming-refine）。
  只消耗不产出的不算 —— 那种是环路的下游消费者，算进来会让边界无限膨胀。
- **规则 B**：某 SCC 物品既无 `mining` 采集来源，又只有少数非采集配方能产出它，则这些配方属于环路（plasma-refining）。

#### H.3 交叉验证结果

自动推导的结果与案例 D 的人工模型**逐项相等**：

| 项 | 案例 D（人工） | 案例 H（自动） |
|---|---|---|
| 配方集 | plasma-refining / reforming-refine / x-ray-cracking | 同 |
| 精炼油需求 | 6.5 /s | 6.5 /s |
| 氢气需求 | 12.0 /s | 12.0 /s |
| 高能石墨需求 | 5.0 /s | 5.0 /s |
| 最优解 | plasma 6.1667、xray 5.8333 | 同 |

这不是循环论证：案例 D 的数字来自案例 B 的手算链条，案例 H 的数字来自图遍历，
两条路径完全独立，结果相同才说明自动化可信。

#### H.4 换目标验证

目标换成能量矩阵 2/s，自动推导给出氢 4.0/s、高能石墨 4.0/s，与配方系数手算一致，
证明推导不是对单一场景的硬编码。

#### H.5 环外副产物必须回供（v4 修正）

v3 的 `derive_demand()` 只累计环外配方对边界物品的**输入**，不抵扣这些配方的**副产输出**。
用当前数据即可复现，不需要第二个物料循环：

```
目标：能量矩阵 2/s + 反物质 1/s

energy-matrix      ×2.0/s :  2 EG + 2 H2 → 1 能量矩阵      ⇒ 耗 H2 4.0/s
mass-energy-storage×0.5/s :  2 临界光子 → 2 反物质 + 2 H2  ⇒ 产 H2 1.0/s
                                                             （同时是反物质的唯一来源）

正确净需求 = 4.0 − 1.0 = 3.0/s
```

v3 把需求记成 4.0/s，油路也净供 4.0/s；加上反物质副产的 1.0/s，整张图多出 **1.0/s 氢气无人认领**——而 LP 自己的三行仍然平衡。这是「局部守恒通过、全局物料不闭合」的典型例子。

修正后的链路：

```
目标 ─► 环外递归展开 ─► 每条配方的实际速率 + 全部输入/输出（ExternalRun）
                          │
                          ├─► 边界物品的外部消耗 gross_in
                          └─► 边界物品的外部副产 gross_out
                                    │
                                    ▼
              b[i] = gross_in[i] + 目标直接[i] − gross_out[i]
```

- 副产**抵扣**净需求（氢气 4 → 3）；
- 副产**超过**消耗时（`b[i] < 0`）写入 `surplus` 并在日志中标注「须由环内吸收或放空」，不静默丢弃；
- 若某副产既不进边界行也无处可去，全局账会出现非零残差并判失败——这正是「不得静默丢弃」的执行方式。

**富余路径有独立回归（H10–H12）。** 目标取「反物质 1/s」时，质能储存副产氢气 1.0/s，而环外没有任何氢气消耗，净需求为 **−1.0**：

```
边界净需求: Hydrogen  0.0000 + 0.0000 − 1.0000 = −1.0000/s
surplus   : Hydrogen 1.0000/s
LP        : 放空列 氢气 1.0000/s，全局账 5 个物品残差全 0
禁止放空  : infeasible —— 富余无处可去，模型直接判死
```

最后一行是关键：它把「富余必须有去处」从一句口号变成一条会失败的约束。

#### H.6 全局物料账：覆盖范围与衔接（v4 新增）

`boundary.global_balance()` 把环内 LP 与环外展开拼成一张账：

```
产出 = 环内净流量 + 环外副产 + 外购
消耗 = 环外消耗   + 目标需求 + 放空
残差 = 产出 − 消耗            （必须为 0，Fraction 精确比较）
```

| 目标场景 | 覆盖物品数 | 其中 | 结果 |
|---|---:|---|---|
| 卡西米尔 1/s | 13 | 3 个边界行 + 目标 + 环外 10 条配方的全部输入输出 | 全部残差 0 |
| 能量矩阵 2/s + 反物质 1/s | 6 | 3 个边界行 + 2 个目标 + 环外 3 条配方 | 全部残差 0 |

双目标场景的解为 `plasma 1.0 / reforming 2.0 / x-ray 4.0`，氢平衡为 `3(环内) + 1(副产) = 4(消耗)`。

**明确不覆盖的部分**（写进日志，不假装闭合）：环内配方的入边原料 `coal` / `crude-oil` 按「边界外无限供给」处理，不建平衡行；没有任何配方的外部原料（如 `log`、`plant-fuel`）单列在 `raw_inputs`。

#### H.7 反证：这套校验真的能抓到那个错误

只证明「修完之后通过」还不够，必须证明「不修就会失败」。H9 用 v3 的口径（H2 需求记 4.0/s）重建同一个模型，再跑同一套全局账：

```
残差  Hydrogen  +1.0000/s      ← 与手算的「多出 1/s」完全吻合
```

若这条反证失败（残差为 0），说明全局校验本身是装饰品。它现在是一条会失败的断言。

#### H.8 一个必须避免的建模错误

案例 H 的第一版用「把松弛列成本置零」来禁用不允许的外购/放空。
结果所有配方速率都是 0、全部靠外购满足需求，**守恒校验依然通过** —— 因为变量仍在约束里，只是求解器不想用它。

正确做法是**让不允许的松弛列根本不进入矩阵**。这条已写入 `case_h` 的实现与注释，
并在 H4b 加了「解未退化为全部外购」的断言。

### 5.2 需要修订

**修订 1：矩阵层应是「SCC 定位 + 边界扩展 + LP」，不是通用方阵求解器。**

- 事实：主口径下 2 个 SCC，其中 1 个是物料生产循环、1 个是储能往返（D.1）。
- 建议：① Tarjan 找 SCC；② **按往返判定剔除状态转换环**（`accumulator` 系列）；③ 求解子图取 **SCC ∪ 入边物品 ∪ 出边物品**，而不是 SCC 本身；④ 松弛列受策略约束（`mining`/`fuel`）；⑤ 求解用 LP + 字典序，而非高斯消元 + 加权。
- 理由：方阵强制（0fuz）会把多配方场景直接判死；无松弛会把副产品净流量变成隐性废弃物（D.3）；不扩边界会让 EG 这类出边副产物失去归属（§4.8.3）；全局开放松弛会给出游戏里执行不了的解（§4.8.1）。

**修订 8：LP 求解器不得锁定为自研，先做 TS 移植验证。**

- 事实：Python 原型已与 GLPK 5.0 在 8 个模型上对齐（§4.7）；**TypeScript 实现尚不存在**。
- 建议：定义 `LpBackend` 接口，默认候选为自研 TS，备选 `javascript-lp-solver` / `glpk-wasm`；TS 版通过同一套 8 个用例后，才允许替换默认实现。
- 理由：初版把「Python 跑通」当成「实现可信」，这是推理跳跃。求解器的可信度来自**与独立实现的对照 + 大规模数值稳定性**，两者都还没有。

**修订 2：「设备数量向上取整」降级为展示选项，不作默认。**

- 事实：`exact` vs `rounded` 差 3.2 倍（4.2）。
- 建议：引擎内部只存分数台数；取整仅发生在展示层与「整栋建筑方案」视图；提供最小整数比（DSP Helper 的 LCM/GCD 方法）。

**修订 3：数据模型必须区分「矿脉配方」与「无配方物品」。**

- 事实：22 条 `mining` 配方，矿石不是无配方物品（2.5.1）。
- 建议：`Recipe.source: 'craft' | 'mining' | 'special'`；`Item.isAutomatable: boolean`；提供显式截断层。

**修订 4：节点 data 只存引用，不存端口副本。**

- 事实：Graph-Calc 反范式化导致 250 行传播函数（2.1.4）。
- 建议：`CanvasNode.data = { recipeId, moduleState?, overrides? }`；端口由 `recipeId` 派生；配合 `useMemo`/selector 缓存。
- 若需要 Ghost Port 语义，改为**独立的一张 `danglingEdges` 表**，而不是污染节点数据。

**修订 5：多配方择优的优先级从 P6 上调。**

- 事实：同一目标不同配方组合差 10 倍设备（4.3）。
- 建议：P3 就提供「按物品切换配方」的手动能力（低成本、高价值）；自动择优放 P5/P6。

**修订 6：功耗必须分 `usage` / `drain` 两项，并标注数据缺口。**

- 事实：DSP Helper 只算 usage；`mining-machine` 在数据集里根本没有 `usage` 字段（实测）。
- 建议：`power = machines × usage + machines × drain × idleFactor`；缺数据时显式标注「该建筑功耗数据缺失」。

**修订 7：`@xyflow/react` 12 的组件不能直接搬 Graph-Calc。**

- 事实：`reactflow@11.11.4` → `@xyflow/react@12` 存在包名变更（`reactflow` → `@xyflow/react`）与节点尺寸字段变更（`width/height` → `measured.width/height`）。**本条为已知版本差异，未在 12.x 环境实测**，迁移时须先跑通最小画布。
- 建议：借鉴设计，重写组件；建立一张「11 → 12 迁移对照表」。

### 5.3 需要补充

**补充 1：求解结果契约。** 采用 Graph-Calc 的形状（`nodeFlows / edgeFlows / problemEdgeIds / bottlenecks / warnings`），并扩展 `stepParents`（FactorioLab 的 `parents` 比例）以支持流向分摊。

**补充 2：数据完整性与可生产性校验。** 案例 E4/E5 表明这两类失败都是静默的。P1 必须有：
- 每个 craft 配方至少一个可用建筑；
- 每个物品要么可生产、要么标记为「不可自动化原料」；
- 每个物品要么可外购（`mining`）、要么不可外购；要么可放空（`fuel`）、要么不可放空——这两条判定要在数据加载期算好并落成字段，不能到求解期才临时判断；
- 配方需带 `excludedByDefault` 标记（`accumulator-full` / `accumulator-discharge` 等状态往返配方）；
- 数据版本与哈希记录在项目文件里。

**补充 3：数值策略。** 用 `Fraction`/大整数做守恒校验与奇异判定（案例 D 的解 `37/6`、`35/6` 是精确有理数）；引擎主算可用 float，但**分类判定（负速率、奇异、欠定）必须用有理数或带 epsilon 的精确比较**，否则 `-1e-16` 会被误判为负速率。

## 6. 数据模型设计（P1 基线）

```ts
// ---- 游戏数据（只读，随版本更新） ----
interface Item {
  id: string;
  name: string;
  nameZh?: string;          // 来自 public/data/dsp/i18n/zh.json
  category: string;
  stack: number;
  automatable: boolean;     // false => log / plant-fuel / df-*
  source: 'item' | 'fluid';
  // ---- v2 新增：LP 松弛策略的数据依据（数据加载期算好，不在求解期临时判断）----
  importable: boolean;      // true <=> 被 flags=['mining'] 的配方产出（18 项）
  ventable: boolean;        // true <=> 存在与自身 fuel.types 匹配的处置设施（27 项，按类型分派）
  ventRoute?: 'thermal' | 'fusion' | 'artificial-star' | 'consumed' | 'transform';
                            // ⚠ 只有 'thermal'（chemical，21 项）当前进 LP；
                            // 其余是已识别的数据关系，见 §7.2.1 的三层划分。
                            // 'transform' 有物料回流（满电池→空电池），必须成对建模。
  fuelValue?: number;       // 燃料热值，用于「放空的能量代价」估算
}

interface Recipe {
  id: string;
  time: number;                       // 单次工时（speed=1）
  inputs:  { item: string; amount: number }[];
  outputs: { item: string; amount: number }[];
  producers: string[];
  flags: ('mining' | 'locked')[];     // technology 配方在导入时剔除
  source: 'craft' | 'mining';
  // ---- v2 新增 ----
  excludedByDefault: boolean;         // 状态往返类（accumulator-full / -discharge），默认不参与求解
  excludedReason?: string;            // 'energy-state-conversion' 等，供 UI 解释
}

interface Machine {
  id: string; speed: number;
  usageKW: number; drainKW: number;   // 缺失时置 null，UI 需显式提示
  modules: number; powerType: 'electric' | 'none';
}

interface Proliferator {
  tier: string; mode: 'products' | 'speed';
  productivity: number; speed: number; consumption: number; sprays: number;
}

// ---- 项目定义（可编辑，跨图共享） ----
interface ProjectData {
  schemaVersion: number;
  revision: number;                   // 单调递增，驱动跨图失效
  itemOverrides: Record<itemId, RecipeId | 'import'>;   // 用户指定某物品用哪条配方
  machineOverrides: Record<recipeId, machineId>;
  // ---- v2 新增：用户对全局策略的覆盖（是否开放由产品决策，见 §13.9）----
  policyOverrides?: {
    importable?: Record<itemId, boolean>;   // 允许「跨星球运来」的物品
    ventable?:   Record<itemId, boolean>;   // 允许「烧掉」的物品
  };
}

// ---- 画布（只存引用与坐标） ----
interface CanvasNode {
  id: string;
  type: 'recipe' | 'source' | 'sink';
  position: { x: number; y: number };   // 永不参与计算
  data: { recipeId?: string; moduleState?: ModuleState; label?: string };
}

interface CanvasEdge {
  id: string;
  source: string; sourcePort: string;   // `out:${itemId}`
  target: string; targetPort: string;   // `in:${itemId}`
  itemId: string;                       // 冗余但受校验，用于快速匹配
}

// ---- 求解输入 / 输出（派生物，永不持久化） ----
interface SolveRequest { nodes: CanvasNode[]; edges: CanvasEdge[]; project: ProjectData; targets: Target[]; }
interface SolveResponse {
  status: 'ok' | 'infeasible' | 'unbounded' | 'invalid';
  nodeFlows: Record<nodeId, { machines: number; inputFlows: Record<itemId, number>;
                              outputFlows: Record<itemId, number>; powerKW: number }>;
  edgeFlows: Record<edgeId, { itemId: string; rate: number }>;
  surplus: Record<itemId, number>;      // 放空量
  imports: Record<itemId, number>;      // 外购量
  problemNodes: string[]; problemEdges: string[];
  bottlenecks: Diagnostic[];
  warnings: Diagnostic[];
}
```

**三条硬约束**（来自原方案，予以确认并强化）：

1. 画布坐标不进入任何计算路径。
2. 节点移动不触发重算（只改 `position`，不改 `data`）。
3. 求解结果不落盘（`stripSolveData`）。

## 7. 计算引擎设计

### 7.1 分层与职责

```
L0  图构建      画布 → 依赖图（校验端口的物品类型、去重、识别多消费者）
L1  递归展开    无环部分：路径作用域 visited + 拓扑序自底向上
L2  循环求解    SCC 内物品：净流量矩阵 + 外购/放空松弛 + LP
L3  配方择优    多配方物品：成本目标下的 LP
L4  后处理      设备台数、功耗、整数比、诊断
```

**关键判据**：L2 的输入规模极小（主口径下物料生产循环只有 1 个、含 2 个物品）。若将来游戏版本引入新循环，SCC 会自动发现，不需要改代码——这正是把「循环检测」而不是「循环白名单」写进引擎的理由。

### 7.2 求解顺序

1. `validateGraph()` —— 端口物品类型、方向、孤立节点、重复边。
2. `buildDependencyGraph()` —— 按 `itemId` 建边，识别每个物品的全部消费者（用于共享合并）。
3. `findSCCs()` —— Tarjan。**每张图只跑一次，结果缓存。**
4. `classifySCCs()` —— 按往返判定（存在 r1/r2 使 `in(r1)==out(r2)` 且 `out(r1)==in(r2)`）把分量分为「物料生产」与「状态往返」；后者在默认求解中剔除（§4.5.1）。
5. **无环区**：从 sink 反向递归，用 `Map<itemId, rate>` 累加需求（这天然实现共享合并）。
6. **循环区**：求解子图取 `SCC ∪ 入边物品 ∪ 出边物品`，对该子图的配方建净流量矩阵，调 LP（§7.2.1）。
7. 合并两个区的结果，得到全局 `recipeRates`；**环形子图的出边物品，其产出先冲抵同物品的外部需求，余额才计入 `surplus`**。
8. 由 `recipeRates` 反推 `nodeFlows` / `edgeFlows`（按生产者产量占比分摊，参考 0fuz 的做法）。
9. 计算设备、功耗、整数比、诊断。

#### 7.2.1 LP 子模型的完整定义

**变量**

| 变量 | 含义 | 取值域 |
|---|---|---|
| `x[r]` | 配方 r 的运行速率（次/秒） | ≥ 0 |
| `s⁺[i]` | 物品 i 的外购量 | ≥ 0，**仅当 i ∈ importable** |
| `s⁻[i]` | 物品 i 的放空量 | ≥ 0，**仅当 i ∈ ventable** |

**约束**

```
Σ_r (out[r][i] − in[r][i]) · x[r] + s⁺[i] − s⁻[i] = d[i]        ∀ i ∈ 求解子图
```

`d[i]` 是外部需求：由无环递归给出，或由用户指定的目标产量给出。**不在子图内的物品不建行**——它们的供需由递归层负责。

**策略集合（数据驱动，在数据加载期算好）**

```
importable = ⋃ { out[r] | r.flags ∋ 'mining' }                       // 18 项
burnable_chemical = { i | ∃ 建筑 m: m.fuel_types ∋ 'chemical'
                          ∧ item[i].fuel.types ∋ 'chemical' }        // 21 项
```

`i ∉ importable` 时 `s⁺[i]` 列**不进入矩阵**；`i ∉ burnable_chemical` 时 `s⁻[i]` 同理。**这一步不能省**：全局开放松弛会给出「把硫酸倒掉」这种游戏里做不到的解（§4.8.1）。

> **v4 更正：`s⁻` 只对应「chemical 燃料进火电站」这一条通道。**
> v3 的文档把燃烧、建筑运行消耗、状态转化合并成一个 `ventable` 集合，再用单物品 `s⁻` 表示处置。
> 这个合并有两个问题：
>
> 1. **与实际代码不一致。** 案例 G/H 的 LP 只用 `can_burn_chemical()` 开列，
>    核燃料棒（聚变站）、反物质燃料棒（人造恒星）、透镜（射线接收站消耗品）、
>    满电池（能源交换站）都**没有**进矩阵。文档若写成「已支持」，读者会高估模型。
> 2. **状态转化会回流。** 满电池经 `accumulator-discharge` 放电后返回**空电池**，
>    只把满电池记成 `s⁻` 会凭空消灭（或凭空产生）空电池。这类处置必须建成
>    「输入物品 → 输出物品」的**成对列**，而不是单物品的减法。
>
> 因此现行实现把处置分成三层，只有第一层在 LP 里：

| 层 | 内容 | 规模 | 是否进 LP |
|---|---|---:|---|
| ① 已建模 | chemical 燃料 → 火电站，记作 `s⁻[i]`（只减物品，无回流） | 21 项 | **是** |
| ② 已识别、未建模 | nuclear → 微型聚变站；antimatter → 人造恒星 | 3 项 | 否（需对应的发电设施在场景中） |
| ③ 已识别、需成对建模 | 透镜 → 射线接收站消耗；满电池 ↔ 空电池 → 能源交换站 | 3 项 | 否（有回流，单列会错账） |

②③ 在 `lib/policy.py` 里以 `Route` 记录（`kind = burn / consume / transform`），
作为**已识别的数据关系**供 P1 设计使用；报告与日志都标注「未实现/未验证」，
不得据此宣称处置能力完整。

**目标（字典序，逐层求解）**

| 层 | 目标函数 | 说明 |
|---|---|---|
| ① | `Σ s⁺` | 外购总量最小 —— 先保供 |
| ② | `Σ s⁻` | 放空总量最小 —— 再省料 |
| ③ | `Σ cost[r] · x[r]` | 运行成本最小 —— 最后省电 |

`cost[r]` 的口径**尚未定稿**（见 §13.5）。当前实现可选「原油当量」作为占位；这是待确认项，不是结论。

**不可行时的诊断要求**：LP 报 `infeasible` 时，必须指出**是哪一行**造成矛盾（哪个物品的净供给为负且不可外购）。只报「无解」对用户没有价值。

### 7.3 数值策略

| 环节 | 数值类型 | 理由 |
|---|---|---|
| 主求解 | float64 | 性能 |
| 守恒校验 | 树模型：float + 容差 1e-6；**边界全局账：`Fraction` 精确比较（残差必须严格为 0）** | v3 此处只写了 float。树模型的 `check_conservation()` 确实用 float（案例 A 首轮的错误是数量级偏差，float 完全能发现）；但 §4.13.6 的全局账要把「副产 1/s」这类整数量级差额算清楚，用有理数可以直接判 `!= 0`，不引入容差 |
| 秩 / 奇异 / 负速率判定 | `Fraction` 或 `eps=1e-9` 精确比较 | 避免 `-1e-16` 误判 |
| 展示 | 格式化 + 最小整数比 | 玩家需要比例，不是 0.3333 |

### 7.4 特殊配方处理器

`fractionator`（重氢分馏）需要专用模型（dsp-chain 提供了三种）。建议接口：

```ts
interface SpecialRecipeHandler {
  matches(recipeId: string): boolean;
  solve(recipeId: string, rate: number, ctx: SolveContext): { machines: number; children: Demand[] };
}
```

默认实现走通用公式，只有注册过的配方走专用模型。

## 8. 画布架构设计

### 8.1 端口约定

```
输出端口 id:  `out:${itemId}`         例: out:circuit-board
输入端口 id:  `in:${itemId}`          例: in:circuit-board
同物品多端口: `out:${itemId}#2`        （极少见，如多目标节点）
```

端口从 `recipeId` **派生**，不存储。派生结果用 `useMemo` 缓存键为 `${recipeId}|${moduleStateHash}`。

### 8.2 连接校验（三阶段）

```ts
function validateConnection(conn, nodes, edges, project): ValidationResult {
  // 1. 结构：source 是 out 端口，target 是 in 端口
  // 2. 物品：sourcePort 的 itemId === targetPort 的 itemId   ← 参考项目全都没做
  // 3. 语义：是否重复边；是否形成环（允许，但标记为「循环」，交由 L2 处理）
  // 4. 可用性：若目标物品在当前项目定义下不可生产，给出警告而非拒绝
}
```

**校验失败必须拒绝落边**，而不是落边后标记。这是与 Graph-Calc 最重要的分歧。

### 8.3 求解结果回填

对齐 Graph-Calc 的做法，但用 selector 而非 effect 注入：

```ts
// 不写入 node.data，避免污染持久化
const nodeFlow = useSolveStore(s => s.nodeFlows[nodeId]);
```

这样 `stripSolveData` 这个环节直接消失——派生数据从一开始就不在节点里。

### 8.4 自动布局

- 传 `ports` 给 ELK，设置 `elk.portConstraints: 'FIXED_SIDE'`，让端口顺序参与交叉最小化。
- 保留 Graph-Calc 的**可撤销**设计：布局前后 diff 位置，提供 undo。
- 布局不改任何业务字段，只改 `position`。

### 8.5 失效处理

替代 Ghost Port 的方案：**独立的 `danglingEdges` 派生表**。

```ts
// 由 edges × 当前端口派生，每次渲染计算，不落盘
const dangling = edges.filter(e => !currentPorts.has(e.sourcePort) || !currentPorts.has(e.targetPort));
```

UI 用红色虚线渲染，提供「重新连接 / 删除」两个动作。节点数据结构不受污染。

## 9. 持久化设计

| 项 | 方案 | 依据 |
|---|---|---|
| 存储 | IndexedDB（`dsp-canvas` 库，`projects` / `graphs` 两个 object store） | 原方案；Graph-Calc 用后端过重 |
| 自动保存 | 800ms 防抖 + 单飞行 Promise + pending 队列 | Graph-Calc 的 `flushStoreSave` 模式 |
| 版本 | `schemaVersion` 存于每条记录 | Graph-Calc `schemaVersion: 7` |
| 迁移 | 读时校验版本，高于当前 → 拒绝并提示；低于 → 顺序执行 `migrations[]` | 原方案要求「旧版本有明确迁移或拒绝策略」 |
| 导出 | 单文件 JSON，含 `schemaVersion` + `gameVersion` + 数据哈希 | 防止用旧数据算新版本 |
| 计算隔离 | 求解在工作线程，失败不影响已保存项目 | 原方案要求 |

**关键**：项目文件必须记录 `gameVersion` 与 `dataHash`。否则用 0.10.29 的配方算 0.11 的项目，会静默错。

## 10. 技术选型

| 技术 | 决策 | 理由 | 替代方案与否决原因 |
|---|---|---|---|
| React 19 | 采用 | Graph-Calc 已验证 React 19.2.4 与 reactflow 11 兼容 | — |
| TypeScript | 采用 | 数据模型复杂，类型是主要防线 | — |
| Vite | 采用 | 三份参考均用 Vite | — |
| `@xyflow/react` 12 | 采用 | 唯一有完整画布实践的路径 | 自研画布：成本过高，无必要 |
| Zustand | 采用 | Graph-Calc 实仓验证，且与「定义层独立成 store」的用法契合 | Redux：样板过多 |
| ELK.js | 采用 | 已验证 `layered` 能满足分层布局 | dagre：分层控制力弱 |
| IndexedDB | 采用 | 本地优先，无后端 | localStorage：容量与结构化能力不足 |
| Web Worker | 采用 | LP + 多目标需要 | 主线程：会卡 UI |
| Vitest | 采用 | 两份参考均用 | — |

## 13. 尚未解决的问题

1. **传送带/分拣器吞吐未建模。** dsp-chain 明确声明不在模型内；0fuz 做了传送带计数但未验证。Dyson Canvas 若要做，需要独立的吞吐层。
2. **采矿设备功耗数据缺失。** `mining-machine` 在 FactorioLab 数据集里没有 `usage` 字段，无法计算采矿功耗。
3. **增产剂「自喷涂」的耦合。** dsp-chain 提供「增产剂自身也被喷涂」的开关（`spraysPerUnit()`），但这会让增产剂需求变成自指方程；正确解法需要迭代或并入 LP。
4. **分馏塔三种模型谁对。** dsp-chain 提供 `dataset` / `belt` / `frac` 三口径，实测结果差异未量化。需要单独一轮验证。
5. **LP 第③层成本的度量口径未定稿。** 字典序前两层（外购、放空）已经是可数、无歧义的；第三层「运行成本」还缺一个客观度量。候选：(a) 原油/矿物当量；(b) 总功耗；(c) 总建筑数。dsp-calct 用的是硬编码的占地/电力权重，不构成依据。**这一条会直接决定 P5 自动择优是否可信，需要在 P1 之前定。**
6. **无解时的用户可操作建议。** 当前只能报「不可行」。能否给出「最小改动集」（如「放开氢气外购即可解」）？这需要在 LP 上做一次弹性分析（elastic LP），技术上可行，工作量未评估。
7. **画布中「未连接端口」的语义。** 一个 `recipe` 节点的输出端口没连线，意味着「不消费」还是「浪费」？需要在语义层定义清楚，否则求解结果会有歧义。
8. **版本迁移的具体策略。** `schemaVersion` 升级时，旧项目的配方引用可能失效（配方 id 变更）。需要设计「配方引用失效」的兜底。
9. **可外购/可放空策略的界面上位。** §4.8 的策略由数据推导，但存在合理的例外：跨星球运输、物流塔补给、手动投料都可以让某些物品事实上「可外购」。第一版是沿用数据推导的严格策略，还是允许用户逐物品开关？——**这是产品决策，需要杨确认**（影响 §6 数据模型是否要加 `userPolicy` 覆盖层）。
10. **状态往返环的排除规则是否要写进数据层。** 当前建议用 `excludedByDefault` 标记 `accumulator-full` / `accumulator-discharge`。但如果将来做能量模块，这两条又要启用。标记的语义需要与「配方可选性」区分开。
11. **自研 LP 的 TypeScript 实现未开始。** §4.7 只验证了 Python 原型。TS 版需要重新实现 Fraction 算术（bigint）与两阶段单纯形，并用同一套 8 个模型回归。**在这之前 LP 后端不得锁定。**

12. **边界自动化的适用范围未验证。** §4.13 的规则 A/B 在「单物料循环 + 无采集来源物品」这个结构上成立，
    并在三个目标场景（卡西米尔 1/s、能量矩阵 2/s、能量矩阵 2/s + 反物质 1/s）上通过交叉验证。但以下情形未测：
    (a) 若将来游戏版本出现**第二个**物料循环，规则 B 的「唯一/少数生产者」判断需要重新定义；
    (b) 若某物品同时有 mining 来源**和**环内产出（例如氢气既有气态巨星又有裂解），当前实现把它归为
    「可外购」，但**没有建模「部分外购 + 部分自产」的最优混合比例**是否被正确求解 —— 案例 D/H 的结果显示
    LP 会自行选择 0 外购，这是否在所有目标下都成立，未做参数扫描；
    (c) 边界物品超过 10 个时的矩阵规模与数值稳定性未测。

13. **全局物料账的闭合范围有限。** §4.13.6 的账目只覆盖「环内平衡行 + 目标 + 环外配方的全部输入输出」。
    环内配方的**入边原料**（`coal` / `crude-oil`）按「边界外无限供给」处理，不建平衡行；
    没有任何配方的外部原料单列在 `raw_inputs`，不参与闭合。因此「全局守恒」的准确说法是
    「在该子图 + 其外部展开范围内闭合」，不是「整张生产图闭合」。
    另外只验证了 3 个目标场景，未做目标产量的随机扫描，也未验证**同一物品既外购又副产**时的账目行为。

14. **顶点枚举的规模上限未突破。** `enumerate_optimum()` 限定 `rank <= 5`、`n <= 24`、组合数 `<= 2e5`，
    超限返回 `too_large`。真实规划（上百变量）下如何获得**算法不同源**的独立基准仍未解决 ——
    可能的路径是对偶证书、区间算术或第二套独立实现，均未评估。
    「超过上限就说不知道」是本轮的底线，不是最终方案。

15. **处置通道只建模了 chemical 燃烧。** 见 §7.2.1。核燃料棒、反物质燃料棒、透镜消耗、
    满电池↔空电池的状态往返都已识别但**未进 LP**；其中状态往返需要成对列（产物回流），
    单物品 `s⁻` 会算错账。在这些通道补齐之前，工具对「副产物能不能消化掉」的回答是不完整的。

## 附录 B · 结论

**Dyson Canvas 应当采用「可编辑图 + 分层求解 + 本地优先」的架构，其中：**

**自行实现（占绝大多数）**

- 画布层：节点/端口/连线校验/失效处理。参考项目只有 Graph-Calc 有可编辑画布，但其连线零校验、端口反范式化，只能借鉴结构不能借鉴实现。
- 数据层：从 FactorioLab 直接导入并归一化，增加 `automatable`、`source`、数据完整性校验。不经 DSP Helper（无许可证且数据同源）。
- 计算层：递归（DAG）+ SCC 定位（含状态往返剔除）+ 边界扩展 + 单循环 LP + 策略化松弛 + 字典序目标。LP 后端走 `LpBackend` 接口，默认实现待 TS 验证后确定。
- 持久化层：IndexedDB + schemaVersion + gameVersion + dataHash。

**可以复用（按 MIT / MulanPSL 条款，保留版权声明）**

- 从 `dsp-production-chain` 借鉴：副产品 `BAL/DEM` 净流量口径、`ceil(x - 1e-9)` 守卫、分馏塔几何衰减模型、瓶颈诊断的三条判据。
- 从 `0fuz/dsp-calc` 借鉴：多生产者边流量按产量占比分摊、增广矩阵构造、负速率显式拒绝。
- 从 `FactorioLab` 直接使用：DSP 数据集（含中文 i18n）、`Step.parents` 的流向分摊思想。

**只能作为设计研究（无许可证）**

- Graph-Calc：定义/画布分层、`projectRevision` 失效传播、Ghost Port 思路、剪贴板载荷校验、布局可撤销、求解结果契约。**全部重写，不复制代码。**
- DSP Helper：`schema.ts` 的数据契约设计、真实数据驱动的测试组织、整数比工具的思路。

**不采用**

- Graph-Calc 的后端求解与 REST 持久化（本地优先更简单）。
- 0fuz 的方阵强制（会把多配方场景直接判死）。
- DSP Helper 的单主配方启发式（10 倍差距的配方选择不能被写死）。
- 任何层级的「取整向下游传播」作为默认。

**一句话结论**：这套技术方案是**可行且必要**的，但真正的难点不在画布，也不在求解器，而在**「同一份数据如何同时喂给画布和计算，又不互相污染」**。Graph-Calc 用 250 行传播函数回答了这个问题，代价是数据结构复杂化；Dyson Canvas 应该用「引用 + 派生」回答它，代价是要严格约束「什么能进持久化」。
